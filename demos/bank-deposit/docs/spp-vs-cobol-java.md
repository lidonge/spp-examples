# SPP 与传统 COBOL/Java 方案对比

按相同业务输入和政策比较，逐阶段补充实际例子。不以代码行数代替复杂度，不预设性能与开发成本优势。

| 维度 | 原 COBOL 或常规 Java | SPP 方案 | 代价与验证需求 |
| --- | --- | --- | --- |
| 偿还规则 | COBOL 工作区及赋值语义、Java 数字 API 与规则交织 | 参与者上的统一数学语法，PHY 选择表示 | 要识别 PIC 截断；编译与生成运算仍需验证 |
| 共享规则 | 子程序/方法复用，接口通常伴随报文或具体对象 | 以角色契约共享校验/计算，APP 选择部署 | 需要重建契约；远程共享数据回写及错误语义要验证 |
| 业务编排 | 段落/方法显式处理调用与分支 | 场景和组共享参与者，校验决定可执行范围 | 当前授权续接与作用域能力尚需检验 |
| 数据与一致性 | 事务、日志、重试结合应用框架和数据库 | 业务计划及守恒与 APP/PHY 事务分工 | 不能省略幂等、锁冲突、提交和恢复协议 |
| 冲正 | 使用原日志反向处理；实现与存储容易耦合 | 原交易角色驱动业务冲正，物理层落实更新 | 必须迁移原成交分量与积数，不能用框架回滚冒充 |
| 工具与运维 | 成熟编译器、调试和生态 | 业务声明可读，生成模型与元数据可检查 | 多层生成链路及来源追踪增加工具成本 |

## 已有证据

前期计算原型能表达普通/呆账两种分配与多个余额关系，14 个源码推导案例通过语句生成与执行。这说明数学表达能力；尚不支持整笔交易、原系统等价、性能或工时结论。

## 每阶段补充方式

P1 给出同输入下 SPP 和参考计算结果及规则位置；P2 展示共享校验/授权契约与调用；P3 比较失败恢复、重复和并发行为；P4 比较原交易冲正与技术回滚。对照实现只覆盖相同契约，未实现部分显式标记，不以简化的 Java 方案衬托 SPP。

## 已迁入规则的具体对照

协定分档原实现依赖五槽工作区及可变输入金额；SPP 用五个参与者、增强 for 和显式量化表达相同选档/分档计算，输入快照与剩余量分离。六项生成服务测试覆盖两种模式及边界，不意味着完整协议读取和日期裁剪已经迁入。

收费原实现穿插机构查询、收费代码选择、客户费率查询、COMP-3 工作区和舍入/限额；demo 将地区/机构分类及公式置于 SPP，客户费率读取置于 APP。真实生成场景验证查询结果进入计算，业务层不选择服务部署地址。常规 Java 也可按同样职责拆分，SPP 的差异在于角色契约、生成调用与数字绑定由语言链路承接；代价是要检查生成代码、元数据和原规则映射。没有测量运行速度或开发工时。

记账与更新阶段，SPP 决定本金/两类利息偿还、存款增减和分录金额，再生成更新后的独立账户快照。JDBC 接口只落实计划、版本条件和共同提交。六项数据库测试验证局部失败、重复和并发；这是与常规 Java 相同的本地事务保障，不能归因于 SPP 数学语法或宣称额外分布式保证。职责分离使业务运算无需嵌入 JDBC，但增加了计划传递、成交记录和生成契约维护成本；原请求级幂等、审计和完整资格到更新仍待接入。

一般现金入口现已将所选资格、授权门槛、收费及记账组成生成场景；APP 承接原请求身份、查询和共同提交，九项整笔测试验证待授权重验、后续成交后的重放及每日累计。常规 Java 同样可实现这些机制，SPP 的具体价值是业务门槛和金额更新仍由参与者上的业务声明表达。新增工具代价也已实际出现：生成场景在构造时查找子服务，demo 必须按依赖顺序装配；多层生成和执行仍需真实场景测试，单纯编译或单原子服务测试无法替代。审批权限、失败审计、全量资格规则和跨日冲正未实现，不作完整银行流程等价结论。

审计阶段已验证成功审计共同提交、失败审计独立保存，以及提交结果未知与已提交返回失败的区别。这些保证来自 APP/PHY 的明确事务与错误处理，常规 Java 可提供同样能力；SPP 不需要引入业务数学语句来实现技术审计。四项新增数据库故障测试说明仅有业务声明仍不足以证明恢复能力，审计存储本身失败及结果查询亦需验证。审批权限、全量资格和跨日冲正仍未完成。

命令行展示现已执行真实生成场景到文件 H2，再查询实际分录与成交形成报告；正常关闭重开也有测试。报告将源公式预期、精确业务数学和 demo 配置分别标注。与传统方案比较的基础是相同输入、相同规则及同样的 JDBC 保障，不能把使用 SPP 当作持久化或崩溃恢复优势；SPP 的优势仍是业务表达和物理数字选择分离，代价仍是生成、装配和事实契约需要共同验证。

积数阶段现在将普通/协定和透支两种期间计算写在 SPP，并把状态、原分量和账务共同保存。六项新增测试证明产品 360 日历不能代替透支 ACT，交易前金额不能误用更新后的金额，技术失败不能只回滚余额而留下积数。这些业务与一致性检查在常规 Java 中同样必要；SPP 的具体收益是组合既有角色服务和统一数学语法，无需在 APP 编写 BigDecimal 运算。迁移代价是必须逐条核对遗留的显式单位、隐式 PIC 截断及调用条件；原第 1 档保存门槛等差异仍需记录，不能只看独立计算公式。

反交易金额阶段，SPP 以原成交角色表达实际逆分量，再复用当前资格服务；七项测试验证量子类金额不覆盖后续操作。传统 Java 同样可以实现正确的 delta 反向，区别在于业务公式不绑定具体数字 API。逆运算也不能自动决定费用退款、追溯计息或非量子生命周期资格；这些都需要明确业务政策，不能把“默认反向公式”宣传成框架可以自动撤销任何业务。

通存与挂失阶段，将原 9704/9709 的账户、机构、柜员及交易例外表达为角色上的共享业务条件。SPP 分开返回两个提示，并组合资格、授权、收费和积数场景；Java 入口仅传递事实及保存成交。传统 Java 也能按此方式拆分，SPP 的收益是业务条件和参与者契约集中可读，代价是解码契约、例外作用域与生成调用必须一起验证。八项新增测试展示普通范围豁免不能用于独立受限子类；类型和语法本身不能替代银行条件核对，也没有性能比较证据。

真实成交查询阶段，APP 按原成交身份读取已提交记录及当前账户，生成场景校验原成交金额关系并形成反向候选。这与传统 Java 同样需要可靠成交记录和当前状态，SPP 的差异在于校验与逆运算由业务角色服务组合。读取后的版本只是一项执行依据；准备成功不能替代新冲正的锁/版本重验，也不能把只读重复准备说成冲正幂等。该分工使尚未确定的退费/跨日政策可以保持显式，但完整冲正仍要连接原记录关联、新身份、账务和审计共同提交。

反向分录阶段，SPP 按已成交的实际科目和金额反向，独立接收退费决定，再校验借贷平衡。传统 Java 也必须核对原载荷与实际账簿、区分核心和收费并保护原记录；SPP 没有让这些规则消失，而是把规则放在可组合的角色服务中。代价是原账簿格式、费用决策和完整冲正事务仍需明确契约；仅有反向公式不会自动解决跨日计息或非量子依赖。

金融组件的实际提交阶段，SPP 根据当前角色与反向金额形成新账户；JDBC 保存独立冲正记录、唯一原交易关联及反向分录，使用当前版本保护并共同保存成功审计。传统 Java 同样可以实现原成交锁、唯一约束与重放，SPP 没有额外产生数据库保证；它的具体价值仍是业务逆运算与物理提交分离。两个业务日志格式分开增加了结果查询及审计汇总成本；只有金额组件通过故障和并发测试，还不足以证明完整银行冲正、跨日积数或 Saga 恢复。

核心冲正资格阶段，SPP 复用挂失服务，但选择独立的销户/取消/冻结规则，而不是复用整个正常存入资格组。传统实现同样需要区分这两条业务路径，SPP 的价值是组的组合和角色契约明确；迁移代价是必须核对实际调用段，方法复用本身不能保证政策正确。文件数据库核对另证明实际反向账簿可读及重放身份保持，这仍来自 JDBC 持久化，不能转化为 SPP 的崩溃恢复或性能优势。

Saga 阶段，原生策略调用明确绑定的业务反交易，保留原存入及后续独立成交；恢复失败不会自动产生补偿。SPP 角色服务继续提供金额及分录计划，APP 绑定局部事务、成交查询和恢复日志。常规 Java 的 Saga 同样需要这些身份、资格和重试机制；SPP 不能消除业务恢复设计，也不能以接口名 rollback 宣称全局技术回滚。持久日志增加了可查询证据，但跨进程回调重建及自动扫描仍有实施成本，当前仅验证进程内明确重试。

现金冲正与量子事务阶段，XBOD 原有效日期、日累计、积数和收费规则进入独立场景源，SPP 明确客户净余额及带符号现金对手方的量子属性和 transaction。实际账户/事实/分录/审计与量子记录共用 JDBC 连接，外层失败回滚全部记录；传统 Java 同样能实现这项单库保障，SPP 的收益是守恒关系、数学表达和事务范围可直接检查。代价是必须处理量子对象身份、与非量子状态共同提交和物理表示，不能只加 quantum 关键字。透支偿还时计息余额与现金金额本身不守恒，净余额才与现金对手方闭合，这项建模也必须在传统方案中明确。通用量子边界反向不是本 demo 整笔银行冲正入口；跨库服务、性能及开发成本仍无实测结论。


## 真实源生命周期的阶段比较

空 catch 缺陷修复后的统一重跑实际通过二十九个 APP 声明式入口，覆盖普通存入、三种债务状态、授权续接、重试、存储费率、拒绝审计、当前账户重校验、现金冲正、版本冲突、写入后故障、日历、内核和协定边界。之前部分入口的假阳性结论已经撤回，证据更正见 source-only-refactoring.md。

| 比较点 | 当前 SPP/APP/PHY 源实现 | 旧 Java 驱动实现 | 当前限制 |
|---|---|---|---|
| 业务顺序及状态 | 待授权、成交、重试、拒绝及源 catch 在场景中可见 | 入口 Java 负责选择场景和装配结果 | 必须逐个迁移旧分支；不能仅以生成成功证明完整语义 |
| 事务边界 | 存款提交与失败审计分别在 SPP 声明 quantum 事务 | JDBC store/入口包装中另行决定边界 | 技术提交结果证据和故障注入还需通用语言及运行支持 |
| 查询与保存 | APP 绑定可选查询、复合身份、插入和版本保护，PHY 绑定存储资源 | 银行 Java 编写查表、保存、注册及共同提交代码 | 声明减少银行技术代码，但提高了编译器和运行库的实现与验证责任 |
| 数字运算 | 业务仍使用乘加和比较表达式，PHY 选择 BigDecimal 表示 | Java 中直接使用具体类型及运算方法 | 数字扩展与业务舍入的责任仍须明确；不能假定一种类型适合所有业务 |
| 验收 | fixture、步骤、独立预期均由 SPP 表达；Maven verify 自动运行 APP 入口 | Java 测试及演示入口手工搭建服务和数据 | 当前顶层及嵌套模型初始化较冗长；不能为缩短 fixture 隐藏业务默认事实 |

现阶段没有达到删除全部手写 Java 的终态，二十九个入口的优势只由其实际覆盖范围支撑。旧实现更直接利用成熟 Java 调试和测试工具；纯源实现需要让生成链路、声明式故障与并发验收承担对应能力，这部分仍在实施。


此次迁移还暴露了生成链路独有的风险：模板吞掉渲染异常会让空方法被误判为成功。修复采用生成前直接检查，通用回归确认异常不能输出场景文件；故障入口另要求实际命中目标服务。传统 Java 直接编译没有此项模板风险，但仍需证明交易和断言确实执行。SPP 的可检查源声明不能替代执行证据，编译器、模板和运行器需要共同验证。

日历验收把原 Java fixture、注册器、异常断言迁为 32 组 SPP 输入及独立预期；旧四项 Java 测试已删除。收益是业务约定与验收均使用同一业务语言，数字 API 和服务装配交给生成链路；当前代价是逐例事实初始化和场景调用较长。没有测量性能或工时收益，不把测试方法数变化当作覆盖率。


内核与协定阶段进一步删除两份旧 Java 测试，SPP 逐项表达金额输出、输入不变性、逐槽量化和错误前无修改。当前源语法的集合构造、增强 for、switch 已足以承接这些固定槽规则；APP 只列出本地服务和验收入口。传统 Java 可以用参数化测试更紧凑地表达案例表；当前 SPP fixture 仍较长，因此按模式和边界拆文件，避免把测试数据简洁性夸大为已具备的优势。清空 target 后的 20 个源入口全部成功，不代表并发或提交点故障也已验收。


协议窗口及准入阶段新增八组日期事实和四十九组准入规则，全部调用源服务，删除日期窗口、控制和准入三份 Java 测试。日期裁剪、警告作用域、严格授权阈值及渠道例外由参与者事实和 SPP 条件直接表达，APP 不选择业务分支。传统 Java 同样能实现这些规则；SPP 的差异是把业务事实、调用、拒绝和独立断言放在业务源中，减少银行 Java 装配代码。当前这些验收场景逐个调用固定案例；按规则拆文件可改善阅读，但不能宣称已消除 fixture 冗长问题。


银行资格阶段，五十四组关系/权限/提示及真实成交/重试/拒绝都由源语言验收；原提示、柜员和账户依据保存在成交记录中，重试读取原记录，不按改变后的提示条件重算。传统 Java 同样需要这个不可变证据；SPP 将关系判断、提示校验、提交顺序及事务模式放在同一可追溯链路，APP/PHY 只承接存储与执行绑定。代价是完整参与者事实初始化较长，并且必须查验实际存储而非只看返回值。八组现金冲正元数据/费用又证明规则可用统一数学语法表达，但不是全账户冲正、完整机构限额更新或分布式保证的证据。


收费库阶段以真实仓储读取替代旧 Java Map 查询，所有分类、折扣、半入和上下限仍在 SPP；当前状态金融反向以原成交分量回退，不按改变后的贷款状态重新分配。传统 Java 可实现相同机制，但需要手工组织数字 API、查询及测试 fixture；当前源语言把这些责任落实为业务公式、显式事务和声明式查询。多层生成仍有编译及追溯成本，不能用统一语法宣称无需存储/恢复设计。十六组费用和十组反向金额仅证明这些责任，不替代整笔业务冲正与分布式恢复。

积数源迁移把协议窗口、日历区别、显式量化、原区间保存和失败重试一起放进 SPP 验收，APP 用通用故障声明替代银行测试中的 JDBC 代理。常规 Java 同样可以实现这些保证；SPP 的具体分工是源场景负责业务计算、边界和审计分类，物理运行层提供测量到的事务证据。语言本身不能消除 commit 确认丢失，也不能把 Saga 补偿解释成技术回滚。结果证据需要后端协议配合，当前没有全远程或多数据库原子保证的验证；新增源验收仍在运行。


积数阶段最终 clean verify 已成功：四个积数入口和七组审计政策实际执行，旧六项积数 Java 测试删除，十四个主 Java 和十个测试 Java 仍待迁移。首次源验收因独立分录预期把总额误写 50 而失败；核对资金来源后修正为现金 50 加存款减少 120、借贷各 170，再取得完整通过。这说明同样需要核对独立预期，生成和统一数学语法不能消除业务分析错误。源审计读取结果证据可避免把 commit 确认丢失误当作已回滚，但不增加物理数据库本身的一致性能力。
