# 对齐最新版 Petstore 的存款演示重构

## 目标与基线

以当前 Petstore 的参与者、默认 CRUD、事务边界、量子 bounds、失败信息和技术服务生成链路为基准，重构存款演示。银行规则仍以已核对的 XBOD 现金存入与现金冲正为准，不把通用反交易替代现金冲正的跨日规则。

2026-10-13 基线：旧源有 102 个文件、SPP 约 11,031 行。编译首先在手续费模块的旧式 query 返回值处失败。历史报告中的成功次数只适用于当时版本，不能作为当前验收证据。

## 功能及业务约束

- 现金存入：入口资格、当日入账、授权等级、手续费、正常/不良/核销透支偿还、积数及平衡分录。
- 现金冲正：使用原成交分量作用于当前账户；不覆盖后续交易；保留 XBOD 同日/跨日、Mode2、明细计数、积数扣回和机构限额条件。
- 开户维护和资金交易分开；现金来源以结算账户相反增量表达，不能凭空初始化余额。
- 银行业务编号保留；技术主键、版本、幂等记录不进入 SPP。合约引用参与者，不使用技术外键替代。
- 场景明确列出参与者，查询原地补全；计算中不校验、不调用普通原子服务；场景不调用场景。
- SPP 只表示事务一致性边界及传播；APP 选择部署和模式，PHY 接入数据库与量子实现。
- 成交值上下限写在调用处，量子服务只表达增量；框架负责越界校验、回填和技术反交易。
- `fail` 读取系统 `ResultInfo.failure`，记录业务拒绝事实；技术故障不作为正常业务资格分支。

## 实施路径

1. 保存旧源的可追溯参考和旧验收条目，区分生产业务规则与测试夹具，不把历史测试场景继续暴露为生产服务。
2. 按 cboddeposit 域的账户、准入、计算、手续费、积数、分录、存款、冲正划分目录；场景各自成文件。
3. 重建明确的角色与场景合约；保留计算公式的来源说明；消除巨型 Work、返回赋值、业务幂等、技术版本和 SPP 异常。
4. 更新默认 CRUD、APP 表/关系、环境部署、数字默认和 PHY 存储；加入拦截所有服务的技术追踪例子。
5. 对齐本地共同提交与分库存储部署；验证资金守恒、成交回填、最小边界与真实失败处置。
6. 运行生成、编译、自动验收及必要框架回归；逐项汇总覆盖与已知问题。只有实际通过的新检查才进入新版验收报告。

## 迁移台账与待确认事项

- 测试形式：按用户后续“测试移出 SPP，需要时由 Java 测试组合场景”的约定，与 Petstore 对齐；Java 测试不实现业务公式。旧验收夹具保存在 legacy-source 作对照。
- 真实银行的授权、产品限额、费率和科目依赖外部配置。演示参数不能宣称等同生产银行配置。
- 业务补偿完整协议仍为全项目未决项；本轮只采用现有 FailureInfo 和显式 fail 能表达且可验证的处置。
- 历史验收条目必须映射到新测试或明确标注尚未迁移，不能用减少验收范围换取“全面通过”。

## 当前实施与行为差异

- 旧主键 query／store 声明改为默认 CRUD；账户、费率、成交合约和分录分别映射自己的表。个性化费率以客户业务登记号及费率代码组合定位。
- 所有生产场景不再调用其他场景；数学中间对象只在计算原子服务内创建；日期、单位、分档和分录校验在场景显式调用。
- 贷款状态、账户状态、授权等级和准入结果使用英文枚举；旧 Normal 账户状态映射为 ACTIVE。
- 缺失费率不再通过返回对象为空及计算里的 require 判断，使用默认查询和主层 checkRequiredFeeIdentified，依据参与者确认状态保留 DEPOSIT_FEE_RATE_NOT_FOUND。授权评估返回 PENDING_AUTHORIZATION 事实，真正存入时再显式 checkCashAuthorization。
- daily cash 等累计由普通事实维护，不重复计入资金；积数使用成交前账户计算，在提交时保存。
- 量子库调用处显式 bounds、成交属性自动回填；现金结算对方可为负，避免凭空初始化账户资金。
- LOCAL 与分库 Saga 失败的结果分别验证；资金技术恢复不等同普通事实业务补偿。详见 KI-R01／KI-R04。
- 修复通用生成器：单域显式 application 也生成环境部署及带域名的服务目录，保证扮演链根实体查询可调用真实提供服务。新增生成器专项测试。

146 个历史业务数据向量已转换为独立测试资源；目前尚不能替代旧 86 个整体验收入口，特别是重启、通信故障和业务补偿项。逐项覆盖与限制在迁移台账维护，未决业务问题按 known issues 记录，不阻塞其他可实施工作。

早期回归次数保留在历史验证记录中，不作为当前状态。内部收款账户资金模型已经按用户约定实现；最新执行证据、适用范围和待补偿限制见 [验证记录](latest-refactoring-verification.md)。

### 有限开户入口核对

新增验收直接使用 JSON 的有限入口，不经过测试辅助数字补零。核对发现默认 insert 仍要求调用者提供显式量子初值，已修正通用仓储：普通开户缺失的量子数值建立零记录，显式非零仍走原有资金初始化限制，不改变本地先插入、独立量子库在本地提交后补建的顺序。开户普通业务初态（正常贷款状态、活动账户、零明细和零积数）在 SPP 计算原子服务中明确建立，不放入 Java 测试。

分库存储验收也修正了隔离问题：每个用例此前只隔离普通记录库，却共享固定的量子库，并重复使用同一业务账户号。新增开户后入账用例留下真实余额后，这种共享会污染后续断言。测试现为普通库和量子库分别分配独立数据源，不通过清零或重置生产量子事实来掩盖问题。

### 账户参与者归属校验

账户、资格和积数各自查询成功，不代表它们属于同一个业务账户。存入和冲正在事务前显式校验三个参与者的账户凭证一致；冲正还核对原成交合约的账户与本次账户相同，避免将另一账户的原成交分量作用于本账户。此项是业务归属约束，不是技术幂等或防重。

网点范围、柜员例外及凭证告警的 54 组历史用例已迁入独立 JSON 验收，通过新版 assessBankQualification 场景执行共享校验与计算；测试不实现地域或告警业务规则。

### 冲正分录完整性

现金冲正除资金与合约状态外，也必须留下反向会计分录。先按原合约查询八条原分录，核对唯一槽位、科目、借贷方向及原成交分量；计算原分录的相反方向，现金手续费槽位按 XBOD 约定全额退回；验证借贷平衡后，与冲正合约、账户元数据共同保存。分录参与者由计算原子服务创建，场景不构造参与者。原分录查询使用合约参与者 key 和 APP 外键关系的默认推导，不重新引入旧 repository 路径配置。

冲正后普通资格事实中的派生净余额以本次量子回填的账户分量重新计算，避免资金已撤销但普通显示余额保留旧成交值。新的 readCashReversal 场景可查询冲正合约及持久化反向分录，便于验收和后续界面展示。

### 冲正明细保存故障

在反向分录插入前注入技术故障：LOCAL 应撤销整笔冲正，保留原成交资金与未冲正状态，可重新发起冲正；统一量子库 + Saga 应反交易量子阶段，但不能把已提交的普通状态和冲正合约当作已撤销。fail 记录待核对，系统保留 RECOVERY_REQUIRED。验收分别读取数据库的资金、原合约、冲正合约及明细，不只看内存结果。

### 独立 JVM 重启验收

用三个独立测试 JVM 依次完成存入、查询原交易并冲正、查询冲正结果与分录。普通记录和量子事实都使用临时文件数据库；重启阶段不重新开户或重置资金，不依赖前一 JVM 的容器、参与者实例或缓存。Java 探针只准备输入和断言，仍调用源语言生成的服务。

### 跨日积数与协议窗口入账

补充真实存储验证：先存入后跨日再存入，积数必须按前次成交余额及经过日数计算，而非本次存入后的余额；重新查询验证持久化积数。协议示例采用旧记录的 650、10 天普通期间与 4 天协议窗口、五级门槛，验证普通积数 4,300 和协议积数 2,200，计算公式不在测试中重写。

原 13 个生产/预览场景各有独立 `cboddeposit-scene-场景名.spp` 文件。开户定义与共享计算移至 account/cboddeposit-10-opening.spp，费率维护定义移至 fee/cboddeposit-50-fee-schedule.spp，冲正共享分录定义仍在 reversal/cboddeposit-10-postings.spp。目录核对没有一个文件包含多个场景。

### 远程调用幂等验收

通过框架的可信 RemoteServiceIngress 注入请求方身份与唯一流水号，验证存入与冲正重放返回原合约编号，查询资金及反向分录确认未重复发生；相同流水号在不同请求方之间不能串用。测试只使用技术协议，SPP 不增加重放/防重分支。此项模拟可信远程入口，不冒充真实网络超时或丢包验证。

### 独立账户并发存入

将两个账户的查询与成交前计算推进到同一技术屏障，再并发执行源场景。两个账户和两个现金结算参与者各自持有不同业务账户号，分别查询数据库验证 100 与 200 的独立资金、原合约归属和明细计数。屏障放在事务外，不用测试同步把两个事务互相锁住。

### 同一远程请求的并发重放

两个测试调用在线程起点同时进入可信远程入口，使用相同请求方及流水号。执行中副本可以返回现行协议的 REQUEST_IN_PROGRESS；原请求完成后重放，核对原合约编号与系统结果，并查询实际资金确认没有重复执行；业务源不加锁、不查询幂等记录。两线程起点同步不等同可控网络重传，验证范围按运行协议记录。

### 真实本机 HTTP 入口

测试启动通用 GeneratedWebServer，使用 APP 生成的暴露目录，经回环 HTTP POST 调用存入与冲正。检查服务器按可信入口覆盖客户端伪造的调用模式/请求方头、相同浏览器请求流水号重放、不重复更新资金，并检查未暴露服务返回 404。端口随机，仅存在于测试生命周期；没有手写银行 HTTP 业务实现。

HTTP 网页 Origin.USER 使用 APP duplicate，而非系统 RPC 的幂等。银行 APP 为存入与冲正增加 5 秒界面防重：本例存入以账户和结算对方区分操作，并用 DepositRequest 核对金额/币种/日期，冲正按账户及原合约核对执行日、明细和 Mode2。Origin.SERVICE 的跨系统幂等仍按可信请求方流水号，LOCAL 不受界面防重影响。

网页防重示例限定核心表单输入，并不证明全部外部资格、费用及授权资料的联合防重。原 facts 语法只接受一个路径，现已扩展为多个参与者/属性路径；其他资料来自可信业务提供方的约定仍见 KI-R03。当前银行 APP 已同时核对 DepositRequest、CashChannel、DepositFeeParty、DepositFeeContext、AuthorizationEvidence，无需巨型 SPP 技术指纹合约。

### 多参与者技术请求事实

APP 防重支持 `facts(DepositRequest, CashChannel, DepositFeeParty, DepositFeeContext, AuthorizationEvidence)`；框架合并各参与者事实用于内容核对，可空可选事实不会被当作业务错误。SPP 不承担请求指纹计算。原单路径配置与元数据接口保持兼容，联合回归及真实 HTTP 内容冲突验收已通过。

### 还本还息的资金对方（2026-10-13 修订）

还息 10 必须增加银行收息内部户 10；现金结算 -100、客户余额 +90、内部户 +10 才是完整资金流。欠息减少是另外的清偿事实。现有八槽分录已表达分配，但不能替代量子账户更新。撤回“仅用欠款负贡献即可解决”的旧假设，不将欠款量子属性降级为普通事实。

本轮已将量子完整更新与资金守恒分组分开，沿用已有 APP 显式属性列表定义资金组；其他被更新的量子属性继续保留成交、bounds、回填及反交易。自动推导仅用于没有显式选择的配置。

新增 InterestIncomeAccount、CollectionInterestIncomeAccount、PrincipalRecoveryAccount 三类内部账户角色，均由 BankAccount 扮演。独立 openBankRepaymentAccounts 场景只做零资金开户，三个同类实体参与者明确命名。现金存入更新对应收款余额，现金冲正按原成交金额反向更新；CashDepositAgreement 保存原结算及内部账户引用，场景核对冲正入口与原成交一致。新场景仍按文件独立保存（共 14 个）。

LOCAL 联合回归已通过真实还本还息、内部户重新查询、跨日冲正恢复欠款、内部户余额边界及后续普通失败时资金共同回滚。分库最终 33 项全部通过，KI-R01 关闭。详细验收项见 KI-R01。

### 历史业务与持久化恢复补充

坏账、核销优先还本以及小数欠款已通过实际存入、数据库查询和现金冲正；原积数、手续费、明细计数和业务日期均有断言。核心冲正资格、例外和前置控制的独立性也已验证。文件库 WRITE_DELAY=0 配置下，成交确认后强制退出 JVM，再启动查询及冲正通过。干净构建共 1,174 项通过，历史入口的未迁移部分继续列明，尤其是授权申请续办与业务补偿。

### 条件查询后的校验作用域

SPP check/identify 默认只结束所在 block。对于“仅适用手续费时查询费率”的场景，if 内只进行查询；主层 checkRequiredFeeIdentified 校验“不适用或费率参与者已确认”，失败时退出场景，之后才校验费率及计算。不能把 identify 放在条件查询块内后误认为会阻止整笔交易。存入与报价均采用此结构；计算预览允许直接提供费率事实，不要求持久化查询身份。

### 现金冲正与通用反交易的敞口差异

归档 `cboddeposit-70-reversal-financial.spp` 的通用反交易使用原 `exposureDelta` 的相反数；`cboddeposit-90-cash-reversal.spp` 则明确说明现金兼容策略不同，按 `principalPaid` 增加敞口。例：原欠本 20、敞口 5，存入偿本 10 后欠本 10、敞口 0，原敞口变化 -5。通用反交易会恢复敞口 5；现金冲正按 XBOD 恢复为 10。

本 demo 执行已确认的现金规则，不将通用反交易案例的敞口 5 期望套用于现金场景。系统因技术失败自动撤销量子阶段仍按实际成交增量反向恢复，与主动发起的业务现金冲正不同。新增持久化验收明确区分原敞口变化 -5 与现金冲正的恢复结果 10，同时核对银行本金回收账户回到零。

### 成交提示和办理事实留存

现金成交合约保存本次 DepositNotices、DepositOperatorFacts、DepositBankProfile 和 AdmissionDecision，供成交后查询还原提示与办理事实。它们是本次输入及评估的业务事实，由 SPP prepareDepositAgreement 明确写入合约；不以技术日志替代。后续调用的参与者变化不能覆盖已保存的原成交事实。外部事实来源的信任问题仍见 KI-R03。

## 原分录科目证据补齐

旧 storedLedgerEvidenceExampleRun 明确拒绝已保存原分录科目被改动。新版仅核对非空科目、金额、方向与归属仍不足。存入合约应保存成交时八条分录的独立快照（不复制反向合约引用，避免环）；冲正先将实际查询分录与此快照比较，再计算反向分录。实现使用 SPP calculate 创建快照参与者，APP snapshot 保存，校验位于场景显式 check，测试以 SQL 技术故障修改已存科目。

## 失败处置再次失败的返回协议

当原交易失败，fail 块保存 CashFailureRecord 又遇数据库故障时，不能覆盖主失败，也不能将 handled 标记成功。系统 FailureInfo.suppressedCodes 应包含第二次失败；主 code、reason、事务结果仍描述原交易。验收通过技术故障使原业务写入失败，再用 H2 触发器拒绝失败记录，检查返回事实、真实资金和无残留处理记录。规则属于通用运行协议，不在银行 Java 中补业务。

## 只读现金冲正试算

新增 previewCashReversal 场景，明确声明当前账户、原成交、资格、容量、积数与候选分录参与者。复用正式现金冲正事务之前的查询、校验与计算，不调用场景，不开启事务，不执行量子或普通更新。试算展示当时的候选事实，不预留额度、不保证未来成交；正式冲正仍重新查询并遵守版本与量子边界。现金按原手续费退回，通用部分退费探索不混入该规则。验收查询持久化账户、原合约和分录，证明试算成功或拒绝均没有成交副作用。
