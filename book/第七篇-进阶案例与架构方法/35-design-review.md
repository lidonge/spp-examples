# 第35章 架构设计评审与能力边界

> © 2026 S++ project contributors. All rights reserved. [Book copyright](https://github.com/lidonge/spp-examples/blob/main/book/COPYRIGHT.md).

角色与服务架构的评审应围绕业务意义、组合关系和执行保障展开。语言声明帮助发现问题，设计者仍需要判断概念是否真实、规则是否完整，以及实现是否兑现了约定。

## 建模方法与架构思想是两个层次

“面向角色的服务架构”包含两个层次：面向角色是一种建模方法，服务架构是一种组织系统的架构思想。为了对照，可以把以对象为建模基础的服务架构称为“面向对象的服务架构”。这两个名称帮助我们分别讨论建模的表达能力和架构的适用领域；面向对象本身也可以用于其他架构。

本书讨论的服务架构面向商业服务领域。购买、付款、预约、发货都有明确的参与身份、办理规则和完成结果，适合通过角色、服务和场景表达。S++ 将这类活动共有的查询、更新、守恒成交与技术接入交给工具，使业务开发者可以用很少的声明表达一项业务。代码简短来自领域中的共同结构和工具提供的能力，复杂规则本身仍需说明。

自然科学中的流体模拟、天体运动或数值求解，关注的主要问题可能是方程、离散方法和误差。将这些问题全部组织为商业服务，通常不方便，也不能期待几句业务声明就替代数值算法。科学计算系统的任务提交、资源安排和结果交付可以采用服务架构，内部求解算法则可以采用适合自身领域的表达。

因此，判断“能否满足任意复杂度需求”，首先要问：是在讨论一种建模方法、一套领域架构，还是当前语言与工具已经支持的功能？这三个问题需要分别回答。

## 面向角色也可以由简单概念构成复杂模型

面向对象从实体出发，把世界看作许多具有状态的对象，再赋予对象动作，通过对象之间的交互描述完整过程。面向角色从行为出发，把世界看作许多活动，再识别参与这些活动的角色，通过行为的组合描述完整过程。场景在这里可以看作一种广义行为：它组织若干行为，共同完成更大的目标。

两种方法都需要表达状态、变化和组合，区别在于建模的起点。面向角色没有取消实体或数据结构；它把这些实体与结构放到所参与的行为中理解。一个复杂过程可以逐层展开为子行为，参与者也可以由更简单的结构组成。只要每一层的状态、规则与组合关系都有明确表达，就可以继续构造复杂模型。

例如，描述一次棋局，可以先建立棋盘和棋子的对象，再提供走子方法；也可以先定义走子行为，识别执棋方、待移动棋子和棋盘这些角色，再组织轮流走子、判定局面与结束棋局。棋盘仍然保存局面，棋子仍然有位置，只是行为成为组织模型的主线。

这说明面向角色的建模方法并不天然局限于商业活动。对于可以由状态与可计算规则描述的过程，两种方法都可以通过组合继续扩展。模型能表达一个过程，与能简短表达、能高效执行是不同的问题。表达能力的构造论证及其条件放在附录 A 的 A8、A9 节。

## 用哈希表比较两种建模起点

哈希表可以直观说明：底层概念简单，并不妨碍它们组合出复杂结构和算法。

面向对象通常先定义一个哈希表对象。对象内部保存一张稀疏的存储表，提供 `put(key, value)` 与 `get(key)` 方法。方法负责计算存储位置、处理冲突、保存或查找记录。我们首先看到的是“哈希表是什么，以及它能做什么”。

面向角色可以先定义“哈希保存”行为，识别三个参与角色：作为查找依据的键、作为待保存内容的值，以及作为存储载体的稀疏表。具体的字符串或编号可以扮演键，某条记录可以扮演值，具体存储结构可以扮演稀疏表。行为说明它们怎样共同完成保存：

```text
哈希保存（键、值、稀疏表）
1. 根据键及表容量，计算候选存储位置。
2. 在该位置检查是否已有相同的键。
3. 已有相同键，替换对应值。
4. 存在其他键，按约定的冲突处理规则继续寻找位置。
5. 找到可用位置，保存键和值。
```

这是一段建模示意，不是当前 SPP 的可执行语法。冲突处理规则可以选择开放寻址；需要扩容时，再定义分配新表、迁移记录和切换存储的行为。复杂性没有消失，而是由几个明确行为共同承担。

“哈希查找”以键和稀疏表为参与角色，按照相同的哈希与冲突处理规则寻找记录，返回找到的值或未找到的结果。保存和查找必须共享这些规则，否则保存成功的值也可能无法找到。

例如，容量为 8，整数键按除以 8 的余数定位。保存键 10 时，先检查位置 2；保存键 18 时，也会检查位置 2。如果那里已经保存键 10，采用向后寻找空位的规则，就把键 18 保存在位置 3。查找键 18 时同样从位置 2 开始，比较键后继续到位置 3，才能取得正确的值。对象方法和角色行为都能表达这套过程。

这里的键和值是算法中的参与角色，不要求把它们声明为 SPP 的业务 Role，也不要求把每次探测都部署为远程服务。这个例子讨论的是面向角色作为底层建模方法的表达能力。第三篇的业务角色、原子服务和场景，是这套方法在商业服务领域中的具体约束与用法。

## 利用现有对象实现承接复杂算法

如果需要，可以围绕面向角色继续构造一门通用语言，为通用数据结构、算法组合和执行方式提供更多表达。当前 S++ 主要服务于商业服务领域，没有必要为了证明建模能力，就把全部通用计算设施重新实现一遍。

面向对象已经积累了丰富的数据结构与算法实现。角色建模可以继续使用这些成果：业务层说明所需能力与结果，APP 声明相应绑定或适配关系，PHY 落实具体 Java 实现和运行资源。一个 Java 复杂对象可以在内部使用哈希表、图结构或数值算法，向业务侧提供明确的能力契约。

例如，配送报价需要根据已准备好的地点和路线网络计算距离。业务层应说明距离如何参与计价，技术适配可以复用 Java 中的路线搜索实现。换用另一种搜索算法，只要仍满足约定的输入、距离含义和精度，就不必改变配送报价的业务规则。会员折扣、能否配送与费用承担等业务决定，仍留在 SPP 中。

这种接入应当通过相应的计算或数据适配接口完成。第五篇介绍的 `before`、`after`、`failure` 拦截器只接收调用元信息，不能用它来替代路线计算或改写业务参与者。这里说明 APP 绑定复杂实现的架构位置，具体绑定形式要以实现提供的接口为准。

这样，复杂需求可以分别落在明确的业务模型和可复用的技术实现中。业务复杂并不要求把算法、数据结构和部署细节全部写进业务语言；需要评审的是分工是否清楚、组合是否完整，以及每一层是否兑现自己的契约。

## 检查模型意义

每个角色应当能说明扮演者、参与行为与自身事实。每份合约应对应明确活动、当事人与约定。每个字段应当说明维护者与用途，业务凭证和技术身份各有归属。

若新角色只是为了包装列表，或合约只是通用返回容器，应重新寻找真实业务关系。若同一属性被多个域独立维护，应检查所有权是否明确。

## 检查服务组合

每项服务需要清楚的职责，场景需要可理解的依赖与完成条件。parallel 之前检查输入、读写冲突和失败汇合，事务之前确认范围和资源，分阶段之后确认恢复责任。

普通 check 失败不自动回滚，REQUIRED 不额外提交，放在同一个进程中运行不改变域归属，远程调用失败也不等于交易未发生。这些判断直接影响业务结果，应在评审中得到具体说明。

## 检查收益与代价

清晰角色和声明式组合可以降低业务与技术混杂，也会把映射、元数据和执行计划的责任集中到生成器与运行时。团队需要能够维护这些能力，并理解生成结果。

如果业务十分简单，新增分层和工具链可能带来额外成本。如果业务存在多参与方协作、复杂规则、资源守恒和多环境部署，显式契约更容易形成可复查的设计依据。是否采用需要结合实际团队与系统条件判断。

## 检查证据层级

语法解析证明表达被接受，编译证明产物在相应层次成立，运行测试证明所测路径，故障与重启测试进一步覆盖特定恢复条件。性能报告还需要明确工作负载和资源。

把这些层级分开，可以避免用一次构建成功支撑所有可靠性结论。已知限制也应随实现版本维护，使设计承诺与实际能力一致。

## 保持架构可解释

一笔业务应当能够沿参与身份、行为、合约、事实归属与执行结果被解释。故障时能定位未完成阶段，变化时能找到责任边界，优化时能识别关键路径。

本书从参与者与行为出发，经由角色和服务形成场景，再通过应用与物理契约走向运行系统。这条联系也是持续评审和演进架构的依据。
