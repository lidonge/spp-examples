## KI-022 通过 APP 绑定 Java 复杂计算实现的接口范围

**作者明确的方向。** 面向角色是一种底层建模方法，不必为商业服务重建通用语言与算法库；复杂计算与数据结构可以复用对象实现，通过 APP 绑定接入。

**当前核对。** `App.g4` 提供 `bind 服务 to qualifiedName`，Petstore 展示跨域服务绑定；已实现的 Java 技术服务扩展由 APP 选择拦截范围、PHY 绑定实现，但 `TechnicalService` 只接收只读调用元信息，不能承担业务计算的输入输出或改写参与者。上述证据不足以确认任意 Java 对象或方法已经可以直接绑定为计算实现。

**待核对与统一。** 需要明确复杂计算适配的服务接口、参与者映射、纯计算约束、数值与失败语义，以及 APP/PHY 的具体绑定形式；若现有接口不足，作为实现扩展处理。不得通过调用观察拦截器隐藏业务计算，也不得把用户提出的架构方向写成已经验证的可执行语法。

**书稿处理。** 第七篇第35章说明建模与接入位置，不给出未经验证的 Java 计算绑定语法；附录 A 的 A8、A9 节说明构造条件与适配契约。

## KI-021 普通更新基于版本的自动冲正

**作者明确的机制。** 普通更新为内置服务，内部没有业务计算，输入由场景准备，因此可以按原事实与本次写入版本自动反交易或冲正。条件是当前版本符合恢复要求，没有后续更新产生的新版本；业务开发者无需独立编写反向计算或对应的补偿服务。

**书稿处理。** 第四篇第21章增加 v8→v9 的地址更新与 v10 后续更新对照，说明原子版本检查、恢复旧事实并生成新版本，以及普通恢复与量子增量反交易的不同条件。跨域混合事务不再把手写普通补偿作为必然要求。

**实现差异。** 当前已同步的 SourceTransactionPlan.compensate 对已提交普通阶段仍要求 CompensationRuleProvider 提供恢复服务名称，缺少时抛出 COMMITTED_STAGE_COMPENSATION_REQUIRED；这一分阶段入口不能作为已实现通用版本保护自动冲正的证据。现有普通查询基线和 revision_token 条件提交可提供基础，但原写入前事实与写入后版本的持久记录、跨域恢复协议及恢复防重仍需核对或实现。不能将此实现缺口改写为架构上必须由业务开发者编写补偿。

**待统一。** 逆序撤销同一记录的多笔已提交更新时，如何识别本事务自身恢复产生的版本与其他请求的新版本；插入、删除、关联成员变化及恢复冲突后的整笔事务处理，需要明确执行契约。恢复版本不能直接退回旧标记，避免旧查询基线重新有效。

## KI-020 普通更新默认乐观锁与事务内自动锁定（实现已核对）

**核对结论。** 普通 update 默认采用乐观锁，并不排除事务内 query 自动锁定。业务 SPP 不显式声明 select for update；当前 JDBC 运行时支持它。此前书稿把不提供显式业务语法误写为没有运行时能力，已纠正。

**实现证据。** SppService 的 `requiresLockedQuery` 与 `transactionQueryInvocation` 分析事务边界、量子字段和普通事实修改意图；TransactionQueryReads 在已声明的事务内传递读保护意图；RepositoryHydratingServiceProxy 的 `effectiveReadRule` 选择 forUpdate；JdbcObjectSnapshotStore 的 `findForUpdate` 使用当前事务连接执行 SELECT ... FOR UPDATE。普通参与者事务内默认锁定；混合参与者仅在同一事务修改普通事实时锁定普通记录；量子事实不加普通读锁。本次静态核对，未重新运行并发测试。

**书稿处理。** 第四篇第19章保留默认乐观锁与并发冲突示例，并补充事务内自动锁定的分类表；与 [事务读取规则](../references/spp-transaction-reads.md)和 [默认乐观保障](../references/spp-optimistic-participant-facts.md)一致。

## KI-019 量子服务的全自动反交易（定义已澄清）

**作者已明确。** 量子服务支持全自动反交易，不需要业务开发者独立编写反交易或对应的补偿交易。SPP 仍负责其他业务失败的处置，技术失败与恢复策略在 APP 层定义。

**书稿处理。** 第四篇第19至21章及附录 D 删除要求业务开发者另行提供量子反向服务、恢复资格或反向补偿交易的表述，解释系统依据原成交记录执行相反增量并保留后续变化。业务完成后另行提出的部分退款、费用调整等按其业务规则办理，与原成交的自动反交易区分。

**执行契约待核对。** 系统如何按原成交事实处理反向范围、后续变化、部分恢复、防重和失败重试，仍需核对不同后端的实现与验证证据。本次为作者定义与书稿修正，不代表已验证所有提供方的完整自动反交易能力；这些实现问题不能转化为要求业务开发者补写反交易服务。

## KI-018 SPP 失败逻辑与遗留异常处理说明（fail 已实现）

**语言与分层。** SPP 不使用 try/catch/throw；业务失败处置采用 transaction/fail。APP 定义技术结果确认与恢复策略，PHY 提供资源能力。结果不明不能直接转换为确定的业务拒绝，但 fail 可据系统事实记录待核对状态，不吞掉原技术失败。

**当前实现。** 主线 6d4bb08d 已加入 fail 语法、TransactionFailureHandling 与内置 ResultInfo/FailureInfo，先完成事务执行和恢复，再执行相邻 fail 块。恢复不确定或 fail 自身失败时，不把原失败当作已处置成功。第一版只支持串行场景的外层事务 fail；多个合约要求显式关联。详见 [系统结果协议](../references/spp-transaction-failure-handling.md)。

**真实案例与证据。** [预约失败处置](https://github.com/lidonge/spp-examples/blob/93d4b68831f1812794e173fd943a77e3be21517a/demos/petstore/docs/reservation-failure-handling.md)记录库存不足、普通保存失败、结果不明及处置失败的业务结果。主线记录 2026-10-13 develop 1,104 项测试通过，含框架 JDBC 量子阶段反交易先于 fail 的验证；不扩大为真实分布式 TCC 或外部量子服务验收。本书此次同步没有重新运行这些测试。

**书稿处理。** 第四篇第19章引用真实预约源片段，第六篇第31章同步拒绝状态和原因，附录 E、F 补充能力与来源。主线 `0fafa21d` 的某银行案例生产源已完成新语法迁移，`try/catch` 只在历史资料中保留，不作为当前可执行示例。附录 F 已改为引用最新验收及明确未完成范围。

## KI-017 Contract 作为上下文与作为扮演者的边界

**实现核对。** 主线 SppDomain 的 `validateRoleTakeBusinessModelDeclarations` 拒绝 Contract 作为 performer，并要求目标为 Role；`validateEnabledStrictAppDeclarations` 在 `strictRoleOnlyBusinessModel` 启用时执行该检查。AppSemanticsTest 的 `roleOnlyBusinessModelValidationRejectsContractRoleTakeDeclarations` 覆盖拒绝规则。本次为源码与测试内容检查，没有重新运行测试。不能把严格模式的拒绝概括为所有配置下一概禁止。

**已有理由。** [业务概念](../references/spp-business-concepts.md)区分合约组成与扮演关系，反对因为 SalesOrder 包含 SalesItem，就写 `take SalesOrder as SalesItem`。合约可以作为后续业务的上下文传入，严格服务边界采用显式 `context Contract`，所以读取和处理合约并不要求它先扮演角色。但这些理由尚不足以证明合约不能扮演任何角色。

**资料对照。** 建模资料 (maintainer reference: `../../../spp/docs/cn/modeling.md`)区分身份契约和可执行契约，并说明契约不是自然实体；预定义契约建模 (maintainer reference: `../../../spp/docs/cn/modeling1.md`)讨论身份契约作为参与者，以及信用卡、存款卡通过共同金融账户身份复用行为。身份契约与当前 Role 含义相关，不能直接把这些例子当作当前 Contract 可以扮演 Role 的证据。所查资料没有给出禁止可执行契约进入后续业务角色的完整论证。

**候选现实需求。** 票据或应收账款在融资中成为抵押标的、不同来源的合约成为统一待审核对象，都可能需要角色多态，以复用估值、资格校验和场景。需要区分作为标的的合约、合约所记载的权利资产、签约方以及内部组成；上述候选并不代表已经决定开放 Contract 扮演。

**待讨论。** 作者提出：服务本来允许传入 Contract，是否已消除扮演需求？直接传入上下文能解决读取与处理，但不自动提供角色多态。应以具体复用案例判断上下文是否足够，或是否需要独立的权利资产 Entity/Reference 扮演角色，再决定是否保留全面禁止规则。

**书稿处理。** 第三篇第14章注明严格检查的启用条件，解释合约上下文与组成关系，不把实现限制写成已经证明的普遍理论结论。

## KI-001 最小服务的定义范围（定义已澄清）

**作者已明确。** 量子服务是一对量子属性组成的守恒服务；其他服务的最小颗粒度是针对一个角色的操作。属性访问和局部运算不再拆成更小的业务服务。多个最小服务可以组合或合并请求，基本定义不变。

**书稿处理。** 第一篇第5章采用成对量子属性的定义，第二篇第11章解释两类最小颗粒度及部署原则，附录 A、D 区分基本服务、内部运算与组合变化组。

**仍需统一的资料与实现表述。** 概念文档 (maintainer reference: `../../../spp/docs/cn/concept.md`)把最小业务活动广泛称为量子服务，需要按作者定义统一名称。现有 calculate/check 可接收多个参与者，quantum update 也可声明多项属性变化：如何区分辅助事实、角色操作的作用对象、多个最小服务的组合以及提交请求，需在语言与实现说明中明确，不能仅凭参数或语句数量判断最小颗粒度。

**某银行实现补充核对（0fafa21d）。** 现金存入与冲正同时更新客户、现金结算及三类内部账户，APP 仅选择真实资金属性参与资金守恒组；欠息、欠款本金与敞口仍作为量子属性记录、校验与反交易。真实还本还息资金去向已经补齐。多属性提交与成对最小服务怎样对应，以及非资金量子事实的守恒对象与分组定义，仍需统一概念说明；不能仅因为实现允许单项增减，就扩大“量子服务是一对量子属性的守恒服务”这一作者定义。正文说明资金与债务事实的差别，不自行改写量子服务定义。

## KI-011 普通更新交换律的规范与实现保障

**已明确的规范。** 作者明确普通更新都是内置系统服务，业务开发者不能编写或修改其实现；内部没有业务查询、计算或校验，全部业务信息由场景中的查询、计算和量子服务提供。量子成交后若还需补充计算与校验，开发者必须用场景串行组规划，输入完整后再启动保存。遵从 SPP 服务规范时，同一事务边界内的普通更新可在量子服务之后并发执行，并符合交换律。

**待核对的保障。** 内置标准 CRUD 已由编译器推导和运行时仓储提供，不再将开发者在更新内部查询、计算或互调作为假设反例。仍需核对同一身份的插入删除冲突、自动业务编号的生成与回填时机、物理外键顺序，以及串行组内的补充计算校验与并发保存之间的执行屏障。

**实现依据。** [事务与存储设计](../references/transaction-storage-v1.md)说明量子阶段之后执行普通更新组；同质源边界保持声明顺序。生成器与事务运行层另有上下文及提交能力，不能仅凭服务不可互调就宣称已经实现所有普通更新的自动并发。

**书稿影响。** 第一篇第7章按作者明确的服务规范阐述并发保存，附录 B 的 B12 节列出完整输入及一致保存的证明条件，第四篇区分执行阶段与实际提交边界。

## KI-012 量子优先自动重排的实现覆盖范围

**已明确的规则。** 作者明确：同一事务边界内，SPP 编译器自动将量子交易提前到所有普通更新交易之前。普通更新不会影响量子交易的结果，量子交易自身可乱序执行；量子阶段之后再并发保存普通事实。

**实现核对。** SppDomain (maintainer reference: `../../lang/src/main/java/com/servpp/lang/models/SppDomain.java`)的 `transactionPlanWarnings` 给混合边界生成量子优先阶段说明；SourceTransactionPlan (maintainer reference: `../../appframe/src/main/java/com/servpp/service/transaction/SourceTransactionPlan.java`)的 `stages` 将 QUANTUM 组放在普通组之前。`executePlan` 对同质、非 SAGA 边界则直接传递原调用列表，[事务与存储设计](../references/transaction-storage-v1.md)也说明同质源边界保持声明顺序。当前证据支持混合阶段的自动量子优先，但尚不能据此认定全部部署模式均已实现同样重排、量子乱序和普通更新自动并发。

**书稿影响。** 第一篇第7章和第四篇第19章按作者规则解释自动计划；附录 B 的 B13 节分别论证量子内部交换、普通更新内部交换和跨类别的单向依赖。

**待讨论。** 自动量子优先计划如何保持场景串行组中成交后计算与校验的依赖？同质 LOCAL 等边界是否同样需要生成量子优先计划？量子逻辑类别与物理事务模式应如何分开用于重排？独立 REQUIRES_NEW 作为边界屏障的处理，以及量子乱序和普通更新并发的实际调度能力，需逐项核对。

## KI-013 微服务颗粒度与可用性的论断范围（已澄清）

## KI-014 默认角色查询的属性裁剪与多级缓存

**作者提出的优化。** 编译时收集角色所有被使用的属性，生成默认查询时只取得该集合所需事实，避免递归读取扮演链全部属性；结合多级本地缓存与远程实体本地缓存，降低角色较大及链条较长的查询成本。

**书稿处理。** 第二篇第11章说明两种优化如何保持角色级服务颗粒度，第三篇第15章明确补全角色不等于加载全链所有属性，附录 C 的 C13 节列出分析、缓存与保存的正确性条件。

**待实现与验证。** 明确编译分析范围，覆盖计算调用、APP 属性访问与输出所需事实；生成按来源的查询字段集合并跟踪加载状态；保证部分查询不导致未加载字段被保存覆盖；明确缓存身份、字段范围、新鲜度、失效及事务读取规则。相关优化由内置查询与 APP/PHY 承接，不开放普通查询服务体给业务开发者修改。

## KI-015 内部主键自动提供与习惯性 ID 警告

**作者已明确。** 编译器为每个实体提供业务不可见的主键，业务开发者无需习惯性定义唯一 ID。对疑似习惯性添加的 ID，编译器给出警告；`business` 声明真实业务用途，用来消除这一警告，不是要求业务人员描述技术主键。

**书稿处理。** 第三篇第13章区分内部主键、习惯性 ID 与业务凭证，解释 `business` 的针对性用途；第12章、第四篇第18章及附录 E 同步采用这一定义。

**实现差异。** SppDomain (maintainer reference: `../../lang/src/main/java/com/servpp/lang/models/SppDomain.java`)的 `validateBusinessFieldMeanings` 目前将没有 business 说明的 id、*Id、*ID 等字段加入 errors，`validateAppDeclarations` 将其合并为编译错误，并非仅给警告。[内置 CRUD 规范](../references/implicit-participant-crud.md)支持 APP-only 主键及内部存储身份，但也明确新记录主键仍依赖 APP 编号或扮演者映射；这不能作为每个实体都已自动创建与分配隐藏主键的完整证据。

**待统一。** 将疑似习惯性 ID 的诊断级别与作者的警告规则统一；明确内部主键自动创建、分配、查询和跨域传递的机制，以及它与实际业务编号、APP 显式主键和已有数据的关系。普通业务主键和技术版本等其他诊断是否采用同样级别，需分别确认，不能一并降级。

## KI-016 mapsame 是否成为默认扮演映射（已澄清）

**作者已决定。** 书稿按照现有实现解释：mapsame 需要显式声明，省略与显式声明不等价；沿扮演链查询与属性映射回填分别说明，不采用默认 mapsame 的设想。

**当前实现核对。** 书稿分支与主线源码中，SppRoleMapper (maintainer reference: `../../lang/src/main/java/com/servpp/lang/models/SppRoleMapper.java`)的 isMapSame 默认 false，解析处理器 (maintainer reference: `../../lang/src/main/java/com/servpp/lang/general/IActasHandler.java`)仅在读取 mapsame 时将其设为 true。映射生成器 (maintainer reference: `../../generator/src/main/java/com/servpp/generator/openapi/MustacheClassWriter.java`)仅在 takeall 或 mapsame 生效时收集同名自动映射。查询运行时 (maintainer reference: `../../appframe/src/main/java/com/servpp/service/runtime/ParticipantRoleQueries.java`)确实沿扮演关系读取来源事实，但最终通过生成的 entityToRole 映射回填，因此递归查询不等于默认同名映射。

**关联影响。** 存储归属检查 (maintainer reference: `../../lang/src/main/java/com/servpp/lang/models/DomainDeploymentValidator.java`)也按 mapsame 标记同名借用属性。将其改为默认，必须同步映射生成、存储归属、身份推导与查询回填，不能只去掉示例中的关键字。联合扮演的同名来源歧义、类型或量子属性不匹配，以及订单成交事实需要独立保存的配置，也要保持明确语义。

**书稿处理。** 第三篇第14章保留显式 mapsame 示例，增加省略 mapsame 的对照，区分扮演链查询与回填，并说明 takeall 是另一种明确的属性继承与映射规则；附录 E 同步更新。该项无需继续讨论是否在正文采用默认 mapsame。
