# 第16章 业务计算规则与集合参与者

> © 2026 S++ project contributors. All rights reserved. [Book copyright](https://github.com/lidonge/spp-examples/blob/main/book/COPYRIGHT.md).

业务计算需要表达金额、数量、资格与政策。S++ 保留开发者熟悉的条件与循环写法，同时将运算含义与物理表示分开。阅读公式时，读者首先看到业务关系，再由 PHY 承接表示能力。

## 把舍入写进业务

明细金额采用单价乘数量，并按约定保留两位小数。`roundHalfUp` 表达明确的舍入规则。若业务没有要求舍入，物理层不能因为数据库容量或默认精度而静默改值。

BigDecimal 是一种可选物理表示，无法精确完成某些运算时仍需要明确的业务舍入或其他表示。使用精确十进制不等于所有数学结果都能有限表示。

## 规则按确定顺序执行

Petstore 报价先计算明细与小计，再根据会员等级计算折扣，之后判断运费，最后形成总额。这些步骤具有事实依赖，规则按执行到当前位置的参与者事实生效。

if、switch、while 与 for 提供确定的控制流程。它们不引入自动反复触发的规则议程，也不允许任意 Java 方法调用。业务公式需要在语言支持的表达和调用契约内完成。

## 集合与内部明细

参与者可以是一维集合，例如 Goods[]。场景查询补全集合，计算遍历商品与购物车明细，形成订单内部的新明细。标量入口实例不能被替换，集合入口保留容器并更新内容。

语法允许声明多维数组，例如 `Goods[][]`，但当前实现尚不支持多维参与者集合的查询、更新与计算操作。本书中的集合示例均采用一维集合；多维支持将在未来出现实际需求时再扩展。

下面是说明汇总职责的示意片段，省略域与其他定义：

```spp
atomic calculate sumOrderLines(ShopOrder) {
    ShopOrder.subtotal = 0;
    for (OrderLine line : ShopOrder.lines) {
        ShopOrder.subtotal += line.amount;
    }
}
```

这段循环按顺序执行。若要并行处理明细，应另外明确分支结果、汇总关系与执行实现。

## 候选事实与成交事实

计算可以把候选订单标记为已付款，但这一内存状态必须通过受保护的更新才能成为实际业务结果。技术失败时也不能把候选状态直接当成已成交状态对外发布。

把计算与更新分开，能让公式独立验证并缩小事务范围。与此同时，需要可靠的版本或成交机制，防止准备事实之后发生的竞争使旧结果覆盖新结果。
