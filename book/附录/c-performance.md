# 附录 C 性能模型与实验方法

> © 2026 S++ project contributors. All rights reserved. [Book copyright](https://github.com/lidonge/spp-examples/blob/main/book/COPYRIGHT.md).

本附录从一项调用的成本开始，推导串行、并行与合并调用的时间，再解释关键路径、容量、完整业务成功率与实验方法。所有数字例子都是假设计算；它们展示模型怎样使用，不代表 Petstore 的实测性能。

## C1 定义一次调用的时间

将第 i 项调用沿真实执行路径的耗时分解为：

```text
lᵢ = cᵢ + eᵢ + qᵢ + tᵢ + dᵢ
```

| 符号 | 含义 |
| --- | --- |
| cᵢ | 传输及通信往返成本 |
| eᵢ | 编解码与适配成本 |
| qᵢ | 在服务、连接和其他资源上的排队 |
| tᵢ | 业务处理及其资源访问的净执行时间 |
| dᵢ | 未计入其他项的事务建立、协调和提交成本 |

这些项必须按测量口径互不重复。若服务端计时包含数据库提交，就应进一步分解，或直接使用整体 lᵢ，不能重复加一次 dᵢ。时间重叠时也不能简单相加，应按后面的路径模型处理。

## C2 串行调用为何累积

若第 i＋1 项必须在第 i 项完整返回后开始，第一个开始至最后一个结束包含各项不重叠区间，因此：

```text
T串行 = h + Σ lᵢ + u
```

h 是共同输入准备，u 是所有分支完成后的公共处理及提交。分支自己的事务若已经计入 dᵢ，不能在 u 中重复计入。

若 n 项调用都承担相同通信 c 和事务 d，省略其他成本：

```text
T细粒度串行 = Σ(c + d + tᵢ)
             = n(c + d) + Σ tᵢ

T一次调用   = c + d + Σ tᵢ
差值        = (n − 1)(c + d)
```

这项差值来自重复调用边界。成立的假设是两种实现具有可比业务工作、相同结果要求，并且一次调用确实能够合并通信和提交。若独立事务表示不同业务阶段，就不能为了公式较小而合并其语义。

## C3 独立分支并行的推导

设分支同时起跑，各自耗时 lᵢ；它们不争用导致额外排队，输入已准备，也不需要彼此等待。所有分支完成的时刻等于最晚结束时刻，因此：

```text
T并行 = h + max(l₁, l₂, …, lₙ) + j + u
```

j 为未包含在分支内的额外调度和汇合成本。由两式相减：

```text
节省时间 = Σ lᵢ − max(lᵢ) − j
并行有净收益的条件：j < Σ lᵢ − max(lᵢ)
```

这个条件说明短任务不一定值得并行。若两个分支各为 1 毫秒，新增调度成本为 3 毫秒，顺序 2 毫秒，并行 4 毫秒。

## C4 一次通信与一次提交的并行模型

若整个组合通过一次入口请求，内部业务活动独立、资源足够，并在一次实际共同提交中完成，可以进一步写为：

```text
T组合并行 = c + d + max(tᵢ) + j
```

它同时减少重复边界并重叠独立工作。但若每个分支仍远程调用，就应保留分支自己的通信；若量子和普通变化分阶段提交，就应保留各阶段成本。不能仅因为使用 SPP 就删掉这些项。

## C5 用完整算例检查公式

设准备 h 为 5 毫秒，查询 l₁ 为 40 毫秒，查询 l₂ 为 70 毫秒，汇合 j 为 3 毫秒，后续 u 为 10 毫秒：

```text
T串行 = 5 + 40 + 70 + 10 = 125 毫秒
T并行 = 5 + max(40, 70) + 3 + 10 = 88 毫秒
节省  = 125 − 88 = 37 毫秒
加速比 = 125 / 88 ≈ 1.42
```

若并行争用让 l₂ 变成 110 毫秒：

```text
T并行争用 = 5 + 110 + 3 + 10 = 128 毫秒
```

此时结果比原串行更慢。不能继续沿用“分支耗时不变”的预测；需要测量争用后的实际 lᵢ。

## C6 一般依赖图与关键路径

对于任意没有循环的依赖图，设节点 v 的执行耗时为 t(v)。在资源无限、无额外调度成本的理想条件下，节点最早完成时间为：

```text
E(v) = t(v)                         v 没有前置节点时
E(v) = t(v) + max{E(p)}              p 是 v 的前置节点时
T理想 = max{E(v)}                   v 是终点时
```

理由是节点只有等所有前置节点完成才能开始，最晚前置完成时刻决定开始时刻。按依赖顺序逐个计算 E，就得到最长依赖路径。

例如查询为 40、70，报价依赖两查询并耗时 10，成交依赖报价并耗时 20：

```text
E查买家 = 40
E查商品 = 70
E报价   = max(40, 70) + 10 = 80
E成交   = 80 + 20 = 100
```

实际调度、资源排队和重试只能在这一模型之外增加或改变相应耗时。优化 40 毫秒分支不会缩短 70 毫秒分支所在关键路径。

## C7 有限资源的下界

若讨论的是同类处理资源，所有节点占用资源的工作量为 W，最多 k 个等效执行槽，则至少需要 W/k 时间。总完成时间也不能短于最长依赖路径 CP：

```text
T ≥ max(CP, W/k)
```

证明第一项：关键路径上的前后活动不能重叠，必须经历其总耗时。证明第二项：长度 T 的区间内，k 个执行槽最多完成 k×T 工作量，所以 k×T 必须至少为 W。

网络等待不应全部算作 CPU 工作，数据库连接也不是 CPU 执行槽。异构系统应对各类瓶颈分别建立资源模型，不能把线程数直接代入上述 k。

## C8 单次延迟与整体吞吐

并行可能降低单次请求时间，同时让每个请求占用多个连接。若数据库每秒只能处理固定工作量，工作没有减少时，吞吐未必增加。

在稳定负载和固定统计边界内，平均在途请求数 L、吞吐 λ、平均停留时间 T 具有计数关系：L = λ×T。可以通过统计窗口内所有请求占据系统的时间，再分别按请求数和时间求平均理解这个关系。它要求系统统计稳定，不能直接用于不断增长的队列，也不能用高分位代替平均值。

因此应同时测量响应时间、吞吐、在途请求与资源利用。只报告单请求改善不足以说明容量。

## C9 实验如何保持可比

选择相同业务输入、数据规模、事实关系、资格、提交保障、协议和资源额度。只改变所研究的调度或部署因素。预热后交替进行多轮对照，避免数据库缓存或运行时编译使固定顺序的一方受益。

串并行实验先保持部署相同；本地与远程对比另作一组。不要一次同时改线程数、存储、提交方式和业务规则，再把全部差异归因于并行。

低负载观察关键路径，高负载逐步增加请求并发，记录何时出现排队、拒绝或资源饱和。通过分支起止事件确认真实重叠，人工延迟只能验证调度，不代替真实负载结果。

## C10 指标与报告

保存各请求的开始、结束、结果类别、重试次数和关联分支。延迟排序后报告中位数和高分位，例如采用最近秩法时，p95 取排序后第 ceil(0.95×N) 个值，并说明计算口径。

成功、业务拒绝、技术失败和超时分别报告。不能删除慢失败后只呈现成功平均值。吞吐明确按完成请求或成功业务计数，重放请求与新成交也要区分。

报告同时保留源码版本、构建环境、资源配置、工作负载、预热和轮次、业务正确性检查、原始记录与分析。Petstore 的功能回归不能代替这里定义的性能基准。

## C11 远程依赖数量与完整业务成功率

先明确本节的口径：讨论一项合法业务能否在约定期限内完整完成。业务资格拒绝不算技术不可用。单次请求的完成概率也不能直接代替按时间统计的服务可用率。

设一项业务必须调用 n 个远程服务，事件 Sᵢ 表示第 i 项调用在期限内成功。若整项业务要求全部成功，则：

```text
P(业务完成) = P(S₁ ∩ S₂ ∩ … ∩ Sₙ)
```

若进一步假设各项成功事件独立，没有重试、替代路径或允许部分完成的规则，且每项成功概率均为 p，则独立事件的乘法规则给出：

```text
P(业务完成) = pⁿ

p = 0.999，n = 20：
pⁿ ≈ 0.980189，即约98.02%
```

只要 0 < p < 1，增加一项必经调用，就把原完成概率再乘以小于1的 p，因而降低完成概率。这证明的是上述依赖模型中增加必经服务的成本，不能推出所有微服务系统的可扩展性与可用性都不可能兼得。

实际调用还可能共用数据库、网络和宿主，事件未必独立。这时需要联合概率或实测结果；不能继续用 pⁿ 预测。重试、冗余、隔离、替代路径和恢复会改变事件定义及依赖结构，需按相应协议重新建模。

## C12 并发、合并与本地部署分别改变什么

对同一组成功事件，串行与并行都要求所有 Sᵢ 成立。若调度不改变各项成功条件，单纯改变启动次序不会改变交集事件。因此，并发主要改善完成时间；在实际期限固定时，它可以减少由串行累积造成的超时，但不能自动消除分支故障。

合并请求减少重复通信与协议边界。若多项量子变化原本分别访问同一执行端，合并后可以由一次请求交付，降低请求级通信失败与结果确认成本。执行端仍要正确完成全部变化，不能把“入口只有一次请求”当作内部资源已不可能失败。

本地部署使细小的计算、校验不再依赖独立的远程进程与网络请求。逻辑服务数量可以保持不变，远程必经依赖数量却可以减少。宿主、存储和本地执行仍有故障概率，需要另外统计；不能直接把原来的 pⁿ 换成 p 并宣称获得相应实测收益。

因此，本书讨论的响应时间收益有三条具体路径：服务规范暴露可并发的依赖关系，量子交换性支持请求合并，本地计算与校验减少细小职责的远程调用开销。这些推导不用于宣称 SPP 改善了微服务远程依赖带来的可用性问题。

验证响应时间收益时，按 C9—C10 在相同业务保障和资源额度下比较，并记录实际远程调用次数、超时与失败。失败请求仍需纳入统计，不能删去慢失败后只呈现成功请求的速度改善。

## C13 属性使用分析与多级缓存

### 查询集合怎样确定

设 R 是一个角色，Uses(R) 是在规定编译范围内，场景、计算、校验、量子调用及其范围表达等实际读取的角色属性集合。应沿计算调用图、属性映射和参与者关系收集依赖，不能只扫描一项服务的直接表达式。

角色查询还需要定位与确认参与者，并为后续存储提供相应技术基线。设 NeededIdentity(R) 为必要身份与定位信息，NeededBaseline(R) 为后续保存需要的版本或其他基线信息，则候选查询集合为：

```text
Fields(R) = Uses(R) ∪ NeededIdentity(R) ∪ NeededBaseline(R)
```

输出页面或外部响应需要的属性也属于使用范围。业务模型没有直接读取、但 APP 实现或输出协议会使用的属性，必须通过可分析代码或明确的依赖声明纳入集合。缺少这些证据时，应采用保守查询范围，不能把未识别的访问当作不存在。

对于从扮演者映射而来的属性，需要进一步求来源依赖。例如 Buyer 的会员等级来自一个角色，收货地址来自根实体，可以分别生成所需来源的字段集合。映射身份、关联定位和身份确认仍要保持，按需查询不等于任意跳过必要的扮演关系。

正确性目标是：在业务需要读取属性之前，该属性已经由对应事实来源补全。未查询的属性应当与实际空值或零值区分，不能因为查询被裁剪就把默认值当成业务事实。查询优化也不改变入口参与者保持稳定的规则。

### 部分查询怎样与保存协作

若查询只读取了部分字段，后续内置保存不能把未读取的字段以空值或默认值覆盖。可采用查询范围与加载状态元数据、明确的写入范围或其他保持未涉及事实的机制；版本比较仍须使用有效查询基线。

因此，按需查询是一项从属性分析到读取、映射和保存共同承接的优化。减少 SELECT 列或远程响应字段只是其中一步，不能独自证明优化后的完整业务与原实现等价。

### 缓存命中需要哪些条件

请求内缓存可以减少同一场景的重复读取，进程内共享缓存可以复用不同请求取得的相对稳定事实。对远程实体，也可以缓存本地角色实际需要的来源事实，再执行角色映射。

缓存身份需要覆盖来源域、参与者身份及必要的业务隔离条件，不能只用对象类型或不完整编号作为键。缓存记录还应标明已加载属性范围；若本次查询要求的集合是 F，缓存已有集合是 C，只有 F 包含在 C 中时，字段范围才满足命中条件。否则应补读缺失部分或重新查询。

刷新与失效可以按事实性质选择版本校验、变更通知或有效期。它们对应不同的新鲜度保证，应由业务要求决定。身份未找到、技术读取失败与缓存过期，也需要分别处理，不能把旧的确认状态无条件沿用。

缓存通常改善读取效率，但不能替代量子成交时的实际范围与守恒检查。缓存余额可以供业务展示或准备阶段参考，成交仍使用执行机制认可的实际事实。事务内受保护的普通读取是否允许使用缓存，同样取决于其版本、隔离和基线要求。

### 性能收益与验证范围

字段裁剪减少读取、传输和映射的数据量，不保证数据库扫描时间按字段数等比例下降。缓存命中减少实际来源访问，收益还取决于命中率、刷新成本、对象大小和并发竞争。

比较时应保持角色、业务规则和保存结果相同，记录字段数量、响应数据量、实际来源调用次数、缓存命中率、响应时间和刷新成本。验证还需覆盖属性遗漏、部分缓存命中、来源数据变化、版本冲突和未加载字段保存，才能确认性能收益没有改变业务含义。

本节给出优化方法与正确性条件，不作为现有编译器已完成属性裁剪或通用多级缓存的验收证据。实现范围记录在书稿外的 KI-014 中。
