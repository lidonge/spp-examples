# 附录 B 交换重排与并行的成立条件

> © 2026 S++ project contributors. All rights reserved. [Book copyright](https://github.com/lidonge/spp-examples/blob/main/book/COPYRIGHT.md).

本附录先证明量子服务增减的交换性：即使作用于同一属性，多个已经确定的变化全部成交后，结果也与执行顺序无关。随后另行证明一般活动的独立读写条件，并讨论并行实现、范围裁决和失败处理。

## B0 量子服务的交换性

设 x 为同一业务维度的属性状态向量，量子服务 A、B 分别表达已经准备好的变化 δ_A、δ_B。参与身份、金额与单位已经确定；服务执行不会用中间余额重新定义这两个变化。对两项均成交的情形：

```text
F_A(x) = x + δ_A
F_B(x) = x + δ_B

先 A 后 B：F_B(F_A(x)) = (x + δ_A) + δ_B
先 B 后 A：F_A(F_B(x)) = (x + δ_B) + δ_A

由加法的结合律和交换律：
(x + δ_A) + δ_B = (x + δ_B) + δ_A
```

因此，两种顺序产生相同状态。这个证明允许 δ_A 与 δ_B 改变同一个坐标，不要求它们的写集合互不相交。例如账户1000元，两项变化分别为−100与−200，两种顺序都得到700元。

若两项服务分别是甲向乙转100、甲向丙转200，可写为：

```text
x = (1000，0，0)
δ_A = (−100，+100，0)
δ_B = (−200，0，+200)

两种顺序的结果均为：(700，100，200)
```

每项变化自身守恒，两项共同结果也守恒。顺序改变可能使中间状态不同，但不改变全部变化成交后的结果；不能把中间读数用于重新计算原本已经确定的转移金额，否则讨论的便不再是同一组变化。

对 n 项变化，任意排列 π 都满足：

```text
x_final = x + Σ δᵢ = x + δ_π(1) + … + δ_π(n)
```

任意排列都可以通过有限次相邻交换得到，每次交换保持结果，所以整体结果与顺序无关。该结论比较的是同一组成交变化。范围竞争怎样决定哪些请求成交、故障时怎样保证变化不丢失不重复，是另需说明的执行契约，见 B7—B9；不能用交换律代替这些保障。

## B1 事实的粒度

把状态看成“事实位置到事实值”的映射。例如：

```text
(买家 A，会员等级) → VIP
(商品 P，销售价格) → 60
(订单 O，折扣金额) → 12
```

同一类型的不同对象是不同位置；同一对象的不同属性也可能是不同位置。分析必须包含实际回填范围。例如 mapper 复制整个对象时，不能只把服务明面上使用的一个字段算作写入范围。

对活动 A，R_A 为它可能读取的全部位置，W_A 为它可能改变的全部位置。条件分支会读取的事实也要计入 R_A。若存在别名，要先判断两个名称是否指向同一事实。

## B2 证明的假设

以下证明限于满足这些假设的活动：

1. A、B 在讨论的输入范围内确定、终止且成功；拒绝和故障另行讨论。
2. R、W 覆盖全部影响，包括条件判断、对象映射和隐藏访问。
3. 活动只根据自身读取事实计算，只改变声明的写入位置；没有额外外部效果。
4. 比较期间没有第三项活动改变相关输入。
5. 无冲突的逻辑事实写入由实现正确承接，最终结果在两项活动完成后观察。

第五项意味着不能用破坏相邻字段、读取半份对象或未定义内存行为的实现替代逻辑模型。

## B3 独立读写的充分条件

设活动 A、B 满足：

```text
W_A ∩ R_B = ∅    A 写的事实，B 不读
W_B ∩ R_A = ∅    B 写的事实，A 不读
W_A ∩ W_B = ∅    双方不写同一事实
```

∩ 表示交集，∅ 表示空集。读集合可以重叠：双方读取相同、稳定的商品价格不会造成覆盖。

## B4 成功状态交换性的逐步证明

从任意满足假设的状态 x 开始，记 A 单独执行后的状态为 a，B 单独执行后的状态为 b。

第一步，A 只修改 W_A，而 W_A 与 R_B 没有交集。因此，B 在状态 a 中读取的事实，与它直接在 x 中读取的事实相同。

第二步，B 的计算确定，所以先执行 A 不会改变 B 计算出的写入值。反向同理：先执行 B 不会改变 A 计算出的写入值。

第三步，逐个比较最终状态位置：

| 事实位置 | 先 A 后 B | 先 B 后 A |
| --- | --- | --- |
| 位于 W_A | A 算出的值，B 不覆盖 | A 算出的同一个值 |
| 位于 W_B | B 算出的同一个值 | B 算出的值，A 不覆盖 |
| 两个写集合之外 | 保持 x 中的值 | 保持 x 中的值 |

写集合不相交，每个位置都属于表中唯一一类，所以两种顺序的最终状态相同。若业务输出只是这些最终事实的确定函数，输出也相同。这完成了假设范围内的证明。

## B5 为什么可以考虑并行

在上述条件下，A 执行期间无法改变 B 的读取事实，B 也不会影响 A。不同位置的写入不会互相覆盖，因此符合物理实现保障的交错执行可以得到同一最终状态。

但业务不能要求同时观察尚未完成的整份状态。例如一条记录的两个字段分别写完之前，对外读取可能看到半份结果。若只允许完整结果可见，就要加入汇合后的发布、合适的隔离或共同提交。

这也说明，交换性证明没有自动获得线程安全或事务原子性。它提供的是允许并行的逻辑条件，运行实现负责正确调度、写入和发布。

## B6 有依赖时的具体反例

设 A 将明细金额设为 120，B 将订单小计设为当前明细金额。初始二者都为零：

```text
先 A 后 B：明细 = 120，小计 = 120
先 B 后 A：明细 = 120，小计 = 0
```

A 的写入与 B 的读取相交，结果不同。并行时 B 若先读取旧明细，也会得到小计零。可以并行的是多条互不干扰的明细计价，汇总仍要等待。

## B7 数学可交换但实现丢失更新

设 A 给余额增加 10，B 增加 20，初始余额为 100。数学上两种顺序都得到 130。但读后写实现可能出现：

| 时刻 | A | B | 余额 |
| --- | --- | --- | --- |
| 1 | 读到 100 | | 100 |
| 2 | | 读到 100 | 100 |
| 3 | 写入 110 | | 110 |
| 4 | | 写入 120 | 120 |

增加 10 被覆盖。原子增量、互斥保护或合适隔离可以避免这一问题，但必须由实现提供。共同写入不符合 B3 的充分条件，其他可并发方式需要另外证明。

## B8 范围约束改变交换结果

钱包为 100，A 扣 80，B 扣 30，余额不许为负：

```text
先 A：A 成功，余额 20；B 被拒绝，最终余额 20。
先 B：B 成功，余额 70；A 被拒绝，最终余额 70。
```

两项增量的代数和与次序无关，但每笔请求是否成功、最终余额均与成交顺序有关。业务若允许竞争者由实际成交顺序决定，可以采用对应执行规则；不能宣称每个请求的结果顺序无关。

## B9 失败与外部观察

A 修改甲，B 修改乙，写集合不相交。A 已独立提交后 B 失败，会留下 A；若 B 先失败且场景停止，则没有 A。于是成功路径交换性不能推广为整个失败过程等价。

若要求二者共同成功，需要共同提交或明确的恢复契约。若允许部分结果，需要把部分结果作为业务状态说明。并行分支报错时，还要知道其他分支是否已完成，而不是只终止等待线程。

通知也是观察。扣款后就通知成功、再等待入账，可能把不完整结果暴露给客户。若通知属于完成后的承诺，就要在成交确认之后发布，并安排通知重复与失败处理。

## B10 校验并行如何汇合

两个校验读取稳定事实，不修改参与者时，可以分别得到通过或拒绝结果。若要求全部通过，汇合结果为：

```text
允许继续 = 校验 A 通过 AND 校验 B 通过
```

AND 的结果与检查次序无关。错误展示若选择“第一个完成的拒绝”，消息会受调度影响；若要求固定业务优先级，就应收集结果后按规定选择。任何“校验失败立即停止”的语言控制还要明确作用范围和对其他分支的影响。

这种论证说明了并行校验需要的契约，不代表任意裸 check 已有对应调度语义。具体表达能力在附录 E 和书稿外的问题记录中说明。

## B11 从两项活动扩展到一组活动

为每项活动建立读写范围，根据数据生产、冲突、观察与提交要求画依赖边。对没有依赖的节点应用上述充分条件。合法执行顺序应满足全部前置依赖。

对两个只在独立节点次序上不同的合法顺序，可以通过相邻独立节点交换逐步转换。每次交换保持上述条件内的最终状态，因此整体成功结果保持。存在共同写入、动态别名或外部状态时，不能直接使用这项推论。

## B12 完整输入下普通更新的交换性

本节讨论同一个事务边界中的普通更新阶段。普通更新由系统内置提供，开发者不能修改其实现，更新内部不做业务查询、计算或校验。查询与计算已经准备事实，量子服务已经完成该阶段所需的增减并补全结果；若成交之后仍需计算或校验，场景的串行组先完成这些步骤。设此时完整待保存事实为 P，普通更新 Uᵢ 只负责把自己承担的部分 Pᵢ 写入存储。

由于 P 已经准备完整，Uᵢ 的写入内容不取决于其他普通更新的执行结果。证明中使用的保存关系为：不同服务保存不同事实；若它们覆盖同一事实位置，则保存的是 P 中同一个已经确定的值。

对任意事实位置 k，比较 U_A、U_B 的两种次序：

| 位置 k | 两种次序的最终值 |
| --- | --- |
| 只有 A 保存 | P_A(k) |
| 只有 B 保存 | P_B(k) |
| A、B 都保存 | P_A(k) = P_B(k) = P(k) |
| 二者都不保存 | 保留原值 |

每个位置的最终值相同，因此：

```text
U_B(U_A(x; P); P) = U_A(U_B(x; P); P)
```

任意数量的普通更新可以通过相邻交换改变执行次序，每次交换都保持结果。因此，同一边界内的这些保存动作可以在量子服务之后并发执行，并在全部完成后汇合。这个论证针对完整业务事实的保存；实际并发执行还需保持事务上下文、保护物理写入并落实共同提交或约定的恢复机制。

例如订单状态、付款金额和凭证内容已经准备好，保存订单与保存凭证分别落库。并发不会改变其输入，也不会改变完整保存的业务结果。若凭证内容需要依据成交结果继续计算，场景必须用串行组先执行计算和校验，再启动保存。交换性证明比较的是输入准备完成后的保存动作，不把前序计算与保存互换。

系统内置更新保证保存内部不混入业务计算、查询或服务互调。场景的串行组保证需要先完成的计算与校验按依赖执行，完整输入与一致的保存关系则用于上述交换性证明。相同身份的插入删除冲突、物理外键顺序和运行层并发能力如何处理，记录在书稿外的 KI-011 中。

不同事务可能携带不同的 P，它们之间仍需版本检查、冲突裁决或其他并发保护。本节的结论不将一个事务内部的交换关系推广成任意事务之间的覆盖写入都可交换。

## B13 为什么量子交易可以自动提前

同一个事务边界内，设量子交易集合为 Q，普通更新集合为 U。按照本书的服务规范：

1. Q 的参与身份、增减量和调用范围由场景准备，U 不再补全或改变这些业务输入。
2. U 保存完整事实，不产生 Q 所需的业务计算结果，也不修改量子属性。
3. Q 内部各项确定增减符合 B0 的交换关系。
4. Q 完成后，依赖成交结果的事实得到补全；若仍需计算与校验，由场景串行组完成，随后 U 按 B12 的保存关系执行。

由前两项，Q 不存在必须等待 U 的业务依赖。将普通保存动作推迟，不会改变 Q 的成交输入或变化关系。普通更新可能需要量子成交结果，因此依赖方向是“量子结果到普通保存”。编译器可以把边界内的量子交易集中到前面，再安排普通更新。

```text
场景准备输入
      ↓
Q：量子交易集中执行（内部可乱序或合并请求）
      ↓
补全成交结果
      ↓
场景串行组：补充计算、校验（按业务需要）
      ↓
U：普通更新并发保存
      ↓
汇合并按事务契约完成
```

Q 内部由交换律保证共同结果不受执行次序影响，U 内部由完整输入下的保存关系保证次序可交换。量子优先的阶段安排则来自二者之间的单向依赖。这三个理由分别说明内部乱序、普通更新并发和跨类别重排。编译器将量子交易提前到普通更新之前，不取消场景串行组明确表达的“成交结果、补充计算、校验、保存”依赖。

重排的是同一事务边界内的执行动作。它不把独立事务并入当前边界，也不自动把多个物理提交阶段变成单一原子提交。LOCAL 可以在共同资源上最终提交；分阶段后端仍需落实自己的提交与恢复协议。规范与具体执行计划实现范围的核对，记录在 KI-012。
