# 附录 A 服务基本模型与形式化推导

> © 2026 S++ project contributors. All rights reserved. [Book copyright](https://github.com/lidonge/spp-examples/blob/main/book/COPYRIGHT.md).

“服务＝参与者×行为”给出了分析业务的起点。本附录先用一笔转账解释符号，再说明怎样分解、怎样组合，以及每个等式究竟在什么意义上成立。符号采用普通文本，所有公式均可在 Markdown 预览中直接阅读。

## A1 参与者与行为共同确定活动

考虑甲向乙转移 100 元。参与者配置 p 包含甲、乙以及本次转账约定；行为 b 说明来源减少、去向增加、范围检查和结果要求。活动 B 由二者共同确定：

```text
B = p × b

p = {来源：甲，去向：乙，转账约定：100 元}
b = 按约定完成资金转移
B = 甲向乙转移 100 元这一业务活动
```

p 不是金额向量，b 也不是一个可参与数值乘法的数字。这里的乘积表示构成关系。把乙改成丙，得到另一项活动；把行为改成余额查询，目标和结果也改变。

“缺少任一项则结果为零”的意思是：缺少必要参与者，或没有实际行为，就不能形成所定义的活动。例如转账契约要求收款方，未指定收款方不能当作一笔金额为零的成功转账。业务拒绝与数值零需要区分。

## A2 先定义我们比较什么

设状态 x 包含参与者的相关事实。对已经确认身份的甲、乙，可以写为：

```text
x = (甲余额，乙余额)
x₀ = (1000，200)
```

一个活动的执行结果还包括业务结果与外部观察：

```text
Exec(B, x) = (执行后状态，结果分类，可观察记录)
```

成功执行转账，状态变为 (900，300)，形成与本次交易身份相连的成功记录。拒绝执行则应保持 (1000，200)，给出相应拒绝结果。通信故障可能暂时无法取得确定答复，其实际状态需要另行查询。

两种实现“业务等价”，必须说明哪些记录需要相同。若只要求资金相同而允许凭证内容不同，是一种等价；若还要求相同原交易关联和重复处理结果，就是更强的契约。业务观察范围由服务定义决定，不能在证明中悄悄缩小。

## A3 完整服务的组合

这里的完整服务采用传统意义上的宽泛概念，例如通常所说的订单付款服务。它可以组合订单查询、归属检查、金额准备、资金转移与凭证记录。用加号表示活动组合：

```text
S = B₁ + B₂ + … + Bₙ = Σ Bᵢ
```

此处 S 表示整项业务，Σ 表示活动组合。映射到 SPP 时，各项明确职责由服务承担，整体组织由场景表达；公式不要求再定义一个普通服务来包含所有调用。组合还包含依赖、提交边界与失败规则，所以不能只给出服务名称之和就认为执行语义已经完整。

例如“资金转移＋订单保存”若共同提交，与资金先提交、订单后提交且需要恢复，是两种执行契约。它们可以以相同成功目标为目的，失败过程和保证范围却需要分别说明。

### 最小服务与组合边界

上述组合以明确的最小服务为组成单位。量子服务由一对量子属性形成守恒变化；其他服务以针对一个角色的操作为最小单位。属性读取、表达式求值和局部赋值属于服务内部表达，不进一步定义为更小的业务服务。

服务所需的辅助事实与服务的作用对象也要区分。例如明细计价可以使用已准备的价格规则，但作用是形成明细角色的金额；转账约定提供金额，量子服务仍以一对余额的守恒变化为最小单位。集合处理、计算复用和量子请求合并可以覆盖多个这样的单位，不改变基本颗粒度。

## A4 按行为分解的分配关系

把复合行为 b₁＋b₂ 定义为：在同一组参与者上，依照明确依赖与边界组合两项行为，则有：

```text
p × (b₁ + b₂) = (p × b₁) + (p × b₂)
```

等式的左边把整体称为一次活动，右边把同一活动展开为两项职责。它成立需要左右保持相同参与者绑定、输入、顺序要求、提交边界和观察规则。

以两条明细计价及汇总为例，单价和数量分别是 (60，2) 与 (20，3)：

```text
明细一金额 = 60 × 2 = 120
明细二金额 = 20 × 3 = 60
订单小计   = 120 + 60 = 180
```

把“逐项计价并汇总”展开为两项计价与一项汇总，仍得到 180。证明依据是汇总读取的正是两项计算产生的金额。若把汇总提前，或改变单项舍入规则，等式需要重新检查。

因此，分配关系说明如何展开定义，并不单独证明子行为可交换。汇总必须等待计价就是一个明确反例。

## A5 按参与方分解的是影响贡献

对转账，甲的贡献是余额减少 100，乙的贡献是余额增加 100。将影响向量展开：

```text
甲的贡献 δ甲 = (−100，0)
乙的贡献 δ乙 = (0，+100)
整体变化 δ   = δ甲 + δ乙 = (−100，+100)

执行后状态 = (1000，200) + (−100，+100) = (900，300)
```

这给出参与方分配式的一种精确解释：

```text
(p甲 + p乙) × b转账 = p甲 × b转账 + p乙 × b转账
```

右边每一项表示同一行为在该参与方上的影响，不是各自再执行一遍完整转账。否则右边会转账两次，显然不等价。

贡献能够分开分析，提交仍要满足整体契约。若仅甲的变化成功，状态 (900，200) 就不符合守恒。相加得到整体变化的计算证明，不能代替实际共同成交的协议。

联合资格也是限制。例如两位申请人共同满足资格，不能直接推断每人各自都满足。参与者分解前要明确哪些部分是局部贡献，哪些规则只能针对整体判断。

## A6 量子服务的交换关系

设量子服务 A、B 的变化分别为 δ_A、δ_B，输入中的参与身份与增减量已经准备。两项变化均成交时：

```text
先 A 后 B：(x + δ_A) + δ_B
先 B 后 A：(x + δ_B) + δ_A

两者相等，执行顺序不影响共同结果。
```

这里允许两项服务作用于同一个量子属性。例如余额1000，分别扣100与200，两种顺序均得到700。它不依赖两个服务写入不同对象，而依赖确定增减的加法交换性。详细证明见附录 B 的 B0 节。

场景中的一般查询、校验和计算还要检查数据依赖，其重排条件在附录 B 中另行论证。范围拒绝与故障恢复如何保持业务要求，也需要相应执行契约。

## A7 业务与技术分离怎样检验

设逻辑业务变换为 F，具体实现为 G，π 将物理记录映射为业务事实。对成功执行，保持业务语义要求：

```text
π(G(物理输入)) = F(π(物理输入))
```

例如数据库金额列用分表示，业务用元表示，π 将 10000 分解释为 100 元。一次 10 元转移，物理实现应转移 1000 分，映射后与业务计算一致。若物理实现转移了 10 分，就不满足等式。

完整契约还要求物理实现保持身份、范围、失败与重复执行语义。技术活动不改变业务目标，并不表示其耗时为零或实现责任为零。

## A8 从对象执行构造角色行为模型

本节论证建模方法的表达能力，不论证当前 SPP 编译器已经支持任意通用程序，也不论证一种表示比另一种更省代码或更快。“复杂”首先指结构、规则与执行步骤可以继续组合，而不是把一个无限过程在有限时间内全部执行完。

考虑一个已经定义清楚的对象模型。它由对象状态、操作及操作组合构成。把对象身份、相关字段和执行位置共同记为状态 x，把一次操作及其输入记为 a，则一步执行可以写成：

```text
对象模型：x --a--> x′
```

这里的状态需要包含会影响后续执行的事实。例如哈希表不仅包含键值记录，还包含容量和冲突处理规则；若扩容会影响后续位置，扩容后的容量也属于状态。若原模型允许多种下一步，例如并发调度，可以把上述关系理解为允许的状态转移集合，而不是单一函数。

为每项对象操作构造一个角色行为：操作目标成为参与该行为的角色，输入值成为必要参与者或行为输入，状态变化遵循原操作规则。一次调用涉及多个对象，就让相关对象分别扮演相应角色。方法调用、条件选择和重复执行，则转为行为间的组合、分支和重复。

设 E 将对象模型状态编码为角色模型状态，构造后的行为记为 b_a。要求每一步满足：

```text
原步骤：x --a--> x′
对应步骤：E(x) --b_a--> E(x′)

业务或算法观察：Obs_role(E(x)) = Obs_object(x)
```

可以据此对任意有限执行序列作归纳：

1. 初始状态按 E 编码，相关事实与观察相同。
2. 假设执行第 k 步后两种表示对应，第 k+1 项操作已有按原规则构造的行为，所以状态变化及相应观察继续对应。
3. 因而执行任意有限步后，角色模型仍能表达对象模型已经描述的过程。

例如对象模型中一次哈希保存经历“位置 2 冲突、检查位置 3、写入记录”，角色模型也按相同规则经历这些步骤。若对象模型先扩容后重排，角色模型必须包含同样的迁移与切换，不能只编码最后的键值集合而丢失对后续行为有影响的事实。

这一构造依赖几个能力：能够保存原模型所需的状态，表达原操作的规则，并支持必要的选择、重复与组合。算法中的这些能力不必具有远程服务、业务事务或商业合约的含义。把 SPP 的领域约束硬套到通用建模上，会改变论证对象。

反方向也可以构造：用对象保存角色模型的参与状态，用方法实现行为，用协调对象组织行为组合。它说明两种建模起点可以承载同一可计算过程；设计是否清楚、实现代价多大，还需要独立判断。

## A9 表达能力、领域简洁性与实现能力

上节给出的是有条件的构造论证。若没有说明状态、规则和组合如何表达，仅以“尚未找到不能模拟的例子”作为依据，还不能完成普遍性证明。一个反例也需要指明究竟缺少哪项表达能力，而不是仅说明一种写法不方便。

讨论现实世界的模拟时，应先确定可观察范围。例如棋局模型记录规则、位置和胜负，不需要同时记录棋子的材质与每个分子的运动。两种模型对指定观察保持一致，才是这里所说的模拟。无限精度的连续事实或不可计算的规则，不能因为换一种建模起点就变成有限计算可以完整处理的对象。

三个不同问题可以据此分开：

|问题|需要说明什么|不能据此直接推出什么|
|---|---|---|
|建模方法能否表达复杂过程|状态、变化与组合的构造，及观察对应关系|当前编译器已实现全部所需功能|
|领域架构能否简洁表达商业服务|角色、服务和场景如何复用领域中的共同结构|所有科学算法都能用几句业务声明实现|
|当前工具能否运行某项需求|语法、绑定接口、数据表示、执行与资源能力|仅凭建模成立即可保证性能与可靠性|

S++ 的简洁性主要来自商业服务领域的共同能力。例如声明付款涉及的参与者、金额和办理关系之后，工具承担标准查询、更新、身份维护和技术接入。若一项需求包含全新的路径搜索算法，算法本身的复杂度仍然存在；可以由已有 Java 实现承担，而不必把它展开为大量业务声明。

复用外部计算时，可以把业务所需结果记为 C，把适配及实现记为 J，输入、输出映射分别记为 encode 与 decode。保持约定需要：

```text
decode(J(encode(业务输入))) = C(业务输入)
```

等式还需覆盖约定的精度、缺失输入和失败语义。路线搜索若约定返回道路距离，实现不能返回直线距离却仍称为等价；输入缺少道路资料，也不能静默返回零距离。若采用近似算法，应把允许的误差写入契约，此时比较的是结果是否满足契约，而不是要求精确值相等。

对纯计算，实现不应隐藏数据查询、持久化或交易副作用，否则场景的依赖和事务边界就不再完整。需要外部数据时，先由相应查询准备，再交给计算；需要保存结果时，仍由场景组织更新。通用算法可以复用对象实现，业务责任不能因此变成技术适配中不可见的规则。

因此，一个复杂需求可以由角色模型表达业务，由 APP 的绑定与适配衔接现有能力，再由 PHY 选择实现及资源。对某个绑定接口尚未支持的能力，应按实现缺口处理，不能把它当作建模方法不能表达该需求的证明。
