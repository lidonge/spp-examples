# 附录 D 量子服务与守恒机制

> © 2026 S++ project contributors. All rights reserved. [Book copyright](https://github.com/lidonge/spp-examples/blob/main/book/COPYRIGHT.md).

本附录用余额与库存说明量子变化、守恒、范围、原子成交和反交易之间的关系。每个结论分别列出数学依据与执行条件，避免用守恒计算代替提交保证。

## D1 将变化写成向量

最小量子服务由一对量子属性组成，表达同一业务维度上的等量反向变化。向量可以放在更大的状态空间中表示这一对属性，也可以表示多个量子服务合并后的变化组；状态空间的维数与最小服务的颗粒度需要区分。

设同一资金维度包含甲、乙、丙三个账户，状态为 x。甲向乙转 100 元：

```text
x = (1000，200，50)
δ = (−100，+100，0)
x' = x + δ = (900，300，50)
```

坐标对应完整参与身份及属性，不能只用“余额”二字定位。金额需要采用相同单位和精度约定。库存则按商品分别建立坐标。

## D2 守恒证明

设总量 Q(x) 为同维度各坐标之和：

```text
Q(x) = Σ xᵢ
Q(x + δ) = Σ(xᵢ + δᵢ) = Σ xᵢ + Σ δᵢ
```

所以，当且仅当增量之和为零时，前后总量相同：

```text
Σ δᵢ = 0  ⇒  Q(x + δ) = Q(x)
```

上例增量合计 −100＋100＋0＝0。若甲减少 100，乙只增加 99，差额为 −1，便不满足所定义的守恒关系。费用如果转入另一个收费账户，应把它作为真实去向纳入模型。

此结论只证明完整向量被应用后的总量。甲先减钱、系统崩溃、乙未加钱，实际状态仍可能破坏守恒，因此还需整体提交。

## D3 独立维度分别证明

商品 P 的可售、预留、已售和供应来源可以表示为：

```text
入库后：        (10，0，0，−10)
预占 2 件后：   (8，2，0，−10)
发货 2 件后：   (8，0，2，−10)
```

每行合计都为零。另一个商品 Q 应有独立等式。P 少一件、Q 多一件，虽然全部件数相抵，仍没有证明 P 的业务数量正确。

金额与件数也不能相加。涉及货币兑换或计量换算时，需要明确汇率、单位、差额来源与舍入政策，不能机械使用直接求和。

## D4 准备输入与实际范围

调用方准备固定金额 a，并约定成交后范围。成交实现读取执行时的余额 x，而不是直接覆盖事前快照：

```text
候选值 xᵢ' = xᵢ + δᵢ
要求：Lᵢ ≤ xᵢ' ≤ Uᵢ
```

null 表示关闭相应方向。范围可以由参与者与合约事实在调用前确定，实际动态余额则由成交机制处理。

初始余额 100，两笔各扣 80 的请求都可能通过事前查询。若第一笔成交后余额 20，第二笔实际候选为 −60，应被拒绝。范围计算必须与受保护更新处于同一成交机制内，不能先检查再无保护写入。

## D5 什么叫整体成交

对一个量子变化组，业务要求成功应用全部 δ，或拒绝时不应用该组变化。执行还要保证未完成的部分状态不被当作成功发布。

一种本地实现可以在同一数据库事务内读取受保护事实、计算、检查并写入，最后共同提交。其保证依赖实际连接、隔离或原子条件写入，以及数据库事务能力。

跨资源实现要提供相应协调与恢复契约。声明“同一事务”不能使多个互不协调的连接自动拥有共同原子提交。量子与普通更新分阶段成交时，也不能把普通阶段失败当作已提交量子组的本地回滚。

## D6 合并提交与增量汇总

设多个量子服务的变化已经确定。由附录 B 的 B0 节，它们全部成交后的共同结果与执行顺序无关。因此，提交方可以将多项服务放进一个量子请求，不需要以逐项发送、等待响应的方式固定次序。执行端接收完整请求后，统一安排变化并处理共同提交。

合并请求可以保留各项变化、请求身份、范围与结果对应关系。若执行契约允许进一步汇总，则按完整参与身份与业务维度求净增量。例如：

```text
甲→乙 100：δ₁ = (−100，+100，0)
乙→丙 30： δ₂ = (0，−30，+30)
净变化：   δ = δ₁ + δ₂ = (−100，+70，+30)
净变化合计 = 0
```

守恒在代数合并下保持，因为各 δ 的和均为零。合并通信与净值汇总是两个步骤：一个大请求可以携带原始变化明细，不必只保留最后的净值。范围检查在逐项与净值两种语义下未必相同。

例如初始为 (0，0)，先甲→乙 100，再乙→甲 100，净变化为零。只检查最终净值会通过；若每个步骤都要求来源不透支，第一步就不允许。逐步检查和净值检查表达不同成交要求。系统必须明确采用哪种边界，不能由最终守恒自动推断业务允许中间透支。

通信收益可以用一个简化模型说明。设有 n 项变化，每次请求的固定通信与协议开销为 h，单项变化数据的传输开销为 p：

```text
逐项请求的通信开销：n × h + n × p
合并请求的通信开销：h + n × p
减少的固定开销：(n − 1) × h
```

这个模型说明合并减少的是重复的请求开销，变化数据本身仍需传输。它不是具体系统的耗时预测；请求大小、响应明细、分片路由与实际协议会影响收益。即使提交端只发出一个请求，执行端也可能需要跨资源通信，因此“一次提交”不能直接理解为后端没有协调成本。

合并后仍需保留识别重复、解释原交易和恢复的证据。净变化为零也不等于业务从未发生。合并的目标是利用交换性降低通信损耗，同时保持原有业务含义与执行保障。

## D7 请求身份与幂等

请求身份应当绑定金额、参与端点、变化组和范围等不可漂移事实。相同身份重试时，若已成功，应返回原结果而不再次应用 δ；若事实改变，则不能当成原请求重放。

这需要持久化的身份与结果证据，并使证据与实际写入具有可靠联系。“先写余额再写去重记录”中间崩溃，可能重复入账；反过来先写成功记录也可能形成记录成功而余额未变。具体后端需要解决这一提交关系。

## D8 反交易为何保留后续变化

设原状态为 x，原成交变化为 δ，此后其他业务产生净变化 e。执行反交易 −δ：

```text
反交易前 = x + δ + e
反交易后 = x + δ + e − δ = x + e
```

因此，增量的反向关系保留 e。余额 100，原增加 50，后续增加 20，反向减 50 得到 120；恢复旧快照 100 则会抹去后续 20。

量子服务由系统依据原成交记录全自动执行反交易，无需业务开发者另外实现反向服务。上述结论要求系统准确保存原成交分量和参与身份，相关变化仍能以加法表示，并保证反向执行不会重复。这些是自动反交易的执行责任；状态赋值或不可撤回的外部效果不能直接套用这一证明。

## D9 自动反交易与后续业务的区别

失败恢复中的量子反交易依据原成交事实恢复该笔变化，不需要业务开发者另外声明反向交易及其补偿逻辑。原成交定位、反向约束的执行机制、持久结果、防重和技术恢复由系统承接，技术处理策略在 APP 层定义。

业务完成后另行提出的退款、冲正或其他变更，需要先明确其业务含义。例如，退货只退部分款项或扣除费用，金额已经不同于原交易的相反增量，应按新业务规则办理，不能仅凭自动反交易推导。原成交值为 δ 的自动反交易是 −δ；新的业务变化若为 δ′，其金额与资格应由该业务确定，不能混为同一操作。

## D10 未知结果与重试

提交完成、响应返回之前断线，调用方看到超时，余额却可能已变化。稳定身份查询应区分已确认成功、已确认拒绝、协议确认未执行和未知。

未知不等于未执行。使用新身份重发可能造成第二次转移；直接补偿也可能撤销一笔并未发生的交易。应当先按后端协议确认原结果或等待恢复证据收敛。

## D11 业务边界与实现范围

| 关系 | 需要确认的实际保障 |
| --- | --- |
| LOCAL | 同 JVM、同实际数据库与 schema、共同连接和提交资源 |
| 非 LOCAL 混合阶段 | 量子组与普通阶段的明确成交顺序、持久结果与恢复规则 |
| REQUIRED | 复用外层边界，不增加独立提交点 |
| REQUIRES_NEW | 独立资源与传播能力，以及外层失败后的处理约定 |
| 不支持的传播或协议 | 构建或部署明确拒绝，不能悄悄降低保证 |

具体示例后端能力见附录 E、F。部署名、协议名与测试通过数量都不能独自证明任意跨资源组合已实现。

## D12 成交后的数值不确定与观测

设请求准备时查询到余额 b，本次已经成交的变化为 δ。从该次查询到成交后观测时刻，其他请求中实际生效的变化集合为 C。若这些变化都可以按同一余额维度相加，则观测余额为：

```text
b_observed = b + δ + Σ eⱼ    （j ∈ C）
```

即使已经确认 δ 成交，若尚不知道 C，就不能只用 b + δ 确定成交后观察到的余额。设 b = 1000，δ = −100，另一请求的变化 e = −200：

```text
另一请求尚未生效：C = ∅，结果为900
另一请求已经生效：C = {e}，结果为700
```

900与700分别对应不同的生效事实，两者都以本次扣除100已经成交为前提。这里的叠加表示成交后、观测前的数值不确定性，不表示数据库同时存放两个余额，也不要求为它们赋予物理量子系统的概率或振幅。已确认的是本次变化成功；仅凭这一确认，还不能知道观测时包含哪些并发变化。

对于同一个已经确定的成交集合，加法给出相同最终值：

```text
(1000 − 100) − 200 = (1000 − 200) − 100 = 700
```

但加法等式不证明所有请求都能成交。例如余额100，两笔分别扣80和30，若要求余额不低于零，就不能同时成功。执行次序与裁决规则可能影响哪笔请求被拒绝。候选状态必须经过范围与成交规则筛选，不能把数学上可写出的每个值都当作合法结果。

成交确认与数值观测回答不同问题。前者回答本次增减是否成功，后者回答观测时属性值是多少。一次准备阶段的查询不能冻结后续变化；一次成交确认也不把余额固定为事前余额加本次增减。观测得到的值需要有明确的读取语义，此后仍可能继续变化。

传统的锁定读、计算新值、覆盖写入，在锁保护期间确定本次结果。量子服务则以增减表达变化，将动态数值与约束交由成交机制处理。这一语义区别并不单独证明后端没有锁：后端仍可能在实际应用增量、检查范围或提交时使用短时锁、原子条件更新或其他协调机制。具体执行能力应由实现证据说明。
