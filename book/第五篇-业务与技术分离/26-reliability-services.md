# 第26章 幂等防重与可靠执行

> © 2026 S++ project contributors. All rights reserved. [Book copyright](https://github.com/lidonge/spp-examples/blob/main/book/COPYRIGHT.md).

一笔付款可能因为页面重复点击、通信重试或结果确认丢失而收到多次请求。可靠执行需要识别这些请求与原业务的关系，避免把重复传输变成重复扣款。APP 定义相应技术策略，SPP 继续说明付款资格、金额和业务结果。

## 幂等识别同一次请求

例如，买家支付 100 元，服务已经成交，但响应未到达页面。调用方使用原请求身份和原内容重试，系统应恢复原来的执行结果，而不是再次扣除 100 元。

当前远程更新协议使用请求方身份、请求方流水号和目标服务识别请求。相同身份、相同内容的重试可以回放原参与者事实与结果；同一个流水号改变金额或收款方，则属于协议冲突。幂等登记不仅保存一个“见过此编号”的标志，还需要区分正在执行、已经完成和需要恢复的请求。

业务订单号与技术请求流水号承担不同责任。一个订单可以有不同办理请求，技术重试则要继续关联原请求；不能每次重试都换一个新流水号，再希望系统自动知道它们属于同一次付款。

## 防重识别短时间内的重复操作

幂等处理的是同一次请求的重复传输，界面防重还要识别用户短时间内发出的多个相似操作。例如，用户连续点击“加入购物车”，两次点击可能产生不同请求流水号，却属于同一次误操作。

APP 可以为页面入口声明防重范围、内容和时间窗口，如同一买家、同一商品、相同数量，在短时间内合并重复办理。窗口结束后，用户再加一次商品可能是合理的新操作，不能永久拒绝。

订单是否允许再次支付则是业务资格，需要 SPP 校验。界面防重窗口过期不意味着订单可以再次付款，幂等期限结束也不意味着原付款没有发生。技术防重与业务规则共同保障办理结果。

当前实现将远程调用幂等与页面防重分开，本地调用不重复登记请求；量子成交内部去重仍由相应量子实现保障。普通查询不通过更新请求幂等协议回放结果，查询缓存是另一项策略。具体配置与协议见 [调用幂等与界面防重](../references/app-call-idempotency-and-duplicate-guard.md)。

## 乐观锁保护不同请求之间的竞争

幂等不能解决所有并发问题。两个不同请求分别修改同一份客户资料，都可能是合法的新请求，却使用了同一份旧事实。

普通更新通过查询基线进行条件提交，发现后续版本时拒绝直接覆盖。量子服务则按增减关系和实际成交范围执行。请求去重、普通版本保护与量子成交分别保护重复调用、竞争覆盖和数量变化，不能只配置一个防重键就替代全部机制。

## 结果确认决定是否可以重试

更新超时可能意味着尚未提交，也可能意味着已经提交而确认丢失。APP 应先依据原请求查询执行结果，或保留技术恢复状态。结果不明时直接重复执行整个场景，可能造成重复扣款或重复创建申请。

已经确认完整撤销、且没有独立阶段提交的请求，可以按协议允许再次尝试；已经部分提交或无法确认的请求需要继续恢复原办理过程。恢复时，量子服务自动反交易，普通更新可以按其版本保护契约恢复，其他业务处置由明确的业务规则决定。相关区别见第四篇第21章。

技术重试也需要期限、次数与退避策略。重试失败不会自动产生一种新的业务补偿政策；超过技术处理能力时，应保存足够的执行证据并进入明确的技术处置流程。

## 拦截器观察可靠执行，执行协议负责确认结果

自定义 Java 技术服务可以关联请求身份、服务名称和技术失败，帮助发现重复调用及异常办理。例如，付款场景入口每次调用都可以留下事件，包括原请求的场景幂等重放；重放没有再次执行原子服务，就不会再次出现对应的业务执行事件。

观察到两次入口调用，不能直接认定扣款发生两次；原子服务出现 `after`，也不能直接认定外层事务已经成交。确认是否重复扣款，仍要核对请求登记、量子流水和业务凭证。

当前 `after` 与 `failure` 是观察阶段，技术服务处理失败不会替换原业务返回或原技术错误。接口不提供自行重试、修改业务结果或独立提交回调，不能在 `failure` 中直接重跑付款。请求幂等、事务确认和反交易继续由相应执行协议承担，拦截器为这些协议提供诊断与观察能力。

## 持久记录让恢复跨越进程重启

如果去重记录只在内存中，服务重启后就可能忘记原请求。对需要重启恢复的更新，应使用满足要求的持久登记与结果存储，并协调登记状态与实际成交事实。

当前框架提供内存与 JDBC 请求存储，二者能力范围不同；结果不明或部分提交的记录不能因普通过期清理被当成全新请求。分库零记录建立也通过持久技术待办恢复，而不是要求业务场景重新实现开户补偿。技术策略集中维护，业务人员才能持续关注办理结果，而不必为每个场景重写一套重试与防重代码。
