# 第24章 缓存与按需数据提升性能

> © 2026 S++ project contributors. All rights reserved. [Book copyright](https://github.com/lidonge/spp-examples/blob/main/book/COPYRIGHT.md).

提升性能不仅是增加并发，还包括减少重复访问、减少无用数据，以及让已经取得的事实得到合理复用。SPP 继续按角色组织业务，APP 可以围绕内置查询、数据传输和接口输出选择优化策略，PHY 提供缓存与存储资源。

## 先用拦截器观察性能，再选择优化位置

可以为查询或场景配置耗时技术服务，通过 APP 的 `after` 和 `failure` 收集服务名称、调用耗时与错误。这样能发现订单耗时主要来自商品查询还是普通保存，无需在 SPP 中增加计时代码。技术人员还可以用 Java 实现新的指标采集器，并通过 PHY 接入现有监控系统。

当前服务拦截器只读取调用元信息，不取得可修改的参与者，也不提供“返回缓存后跳过原查询”的协议。因而耗时观察可以直接接入，查询缓存、按需字段读取和返回数据裁剪则要在查询、仓储或输出适配中实现。它们同属技术层能力，各自使用适合的扩展位置。

## 缓存减少重复访问

例如，购物车有十条商品明细，多条明细使用同一类商品资料。请求内缓存可以复用已经取得的事实；进程内共享缓存可以服务不同请求；多个应用实例还可以通过共享缓存减少对来源域的重复访问。

对于远程产品域，本地缓存商品名称、分类等相对稳定的资料，可以减少网络等待。商品展示仍调用角色查询，缓存命中后由技术层完成事实补全，场景无需手写“先查缓存，再查数据库”。

缓存必须区分参与者身份、字段范围和版本。取得过商品名称，不等于取得过它的价格与销售状态。缓存刷新和失效策略也要符合用途：展示名称可以采用较宽松的时效，实际成交必须由相应执行机制检查权威事实。缓存余额只能辅助展示或准备，不能替代量子成交。

## 按需查询减少读取的数据集

角色可能沿扮演链包含大量属性，一次报价却只用到会员等级、商品单价和数量。可以在编译时收集角色被使用的属性，形成默认查询所需的数据集合，再由查询实现按来源取得这些事实。

例如，Buyer 的资料包含姓名、头像、地址与会员等级。优惠计算只需要会员等级，就没有必要为它读取头像和整份地址；下单还需要地址时，再把相应事实纳入查询范围。服务颗粒度仍是对 Buyer 的查询，优化的是实际加载的数据量。

查询还要保留必要的身份和内部基线，并标明哪些属性已经加载。没有查询到的地址不能被当成空地址保存，否则一次性能优化就会变成数据丢失。部分加载与普通保存之间需要明确协议，不能仅靠生成一条更短的 SQL。

## 按需返回减少传输的数据集

场景执行需要的事实与页面展示需要的事实并不相同。报价可能使用会员等级、地址、商品完整定价信息，页面却只展示商品名称、数量、单价和总额。

APP 可以定义不同入口的输出字段集合：订单列表返回订单号、时间、金额和状态；订单详情返回明细；付款结果返回办理凭证与系统结果。业务角色和合约仍保持原有含义，输出适配只选择入口允许且需要展示的数据。

按需查询决定系统取什么，按需返回决定接口给什么。即使场景内部需要某项敏感事实，页面也未必应当收到它。输出选择还要与权限、脱敏及幂等结果回放保持一致。

当前生成网页接口主要返回执行后的入口对象及结果信息，通用的按需输出方案需要进一步扩展；按角色属性使用集合裁剪默认查询及通用多级缓存，也应按各自实现范围核对。本节说明优化方法，不把这些方案一概视为当前已完成的能力。查询、缓存与部分保存的详细条件见附录 C 的 C13 节。

## 批处理与执行路径优化

同一业务需要取得多个独立商品时，可以批量查询或并发查询，减少串行等待。多个量子服务可以合并请求，减少通信损耗；输入已准备完整的普通更新，也可以按执行计划并发办理。

计算和校验通常可以部署在场景所在进程，直接使用已补全的事实，避免为短小计算增加网络调用。压缩较大的传输数据可以减少带宽消耗，但也增加编码与解码成本，应根据实际数据量选择。

优化效果应同时观察完整场景耗时、读取与返回的数据量、缓存命中和来源访问次数。例如，一个订单列表响应变快，却因详情接口反复补查增加了总访问量，就还需要调整数据集合。实验方法见附录 C。
