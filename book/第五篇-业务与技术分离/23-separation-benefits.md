# 第23章 业务与技术分离的主要收益

> © 2026 S++ project contributors. All rights reserved. [Book copyright](https://github.com/lidonge/spp-examples/blob/main/book/COPYRIGHT.md).

一笔付款的业务要求是：符合资格的付款方向收款方支付约定金额，形成可以核对的办理结果。加密通信、查询缓存、重复请求识别和数据库接入，都在帮助这项业务可靠执行。S++ 把业务要求写在 SPP，把技术策略放在 APP，把实际资源与协议落实到 PHY，使三类工作各自有清楚的维护位置。

## 让业务人员能够直接检查业务

例如，会员折扣从九折改为八五折，业务人员需要核对适用身份、优惠比例和报价结果。若规则混在数据库访问、接口转换与重试代码中，就必须先理解大量技术细节，才能判断改动是否完整。

在 SPP 中，折扣由计算服务表达，适用条件由校验服务表达，场景说明何时调用。需求人员可以沿着这些表达审查业务，也可以与 AI 配合完成建模。默认查询、保存和接口接入由工具提供，业务审查集中于业务事实与规则。第三篇第12章介绍了这种分工怎样降低 AI 必须自由生成和维护的代码量。

技术工作因此也更集中。缓存命中率低，应检查数据访问与缓存策略；重复请求造成重复办理，应检查请求识别与执行协议。这些问题有自己的位置，不必先修改会员折扣或付款公式。

## 同一业务可以适配不同环境

客户资料可以来自本地数据库，也可以来自远程客户域；通信可以采用不同协议，敏感字段可以使用不同的保护方案。业务场景仍然使用买家角色，并按相同业务要求计算与成交。

例如，把客户域从同一个进程迁移到独立应用，需要调整 APP 的服务绑定和 PHY 的端点、资源配置，重新核对事务与恢复能力。只要提供方仍兑现原来的业务约定，付款场景不必增加 HTTP 报文转换或连接管理代码。

技术替换需要保持的不只是类型，还包括事实含义、更新效果和失败结果。旧接口返回“资料不存在”，新接口不能把网络超时也当成不存在。分离让适配责任明确，也使这种差异能够在接入层被发现和验证。

## 技术能力能够集中复用

订单、预约、充值都可能需要识别重复请求。如果每个场景分别实现登记、加锁、保存结果和超时恢复，细小差异就可能导致不同的重复执行行为。由技术层提供统一协议，各场景按需要配置，可以减少重复实现，并集中改进其可靠性。

加解密、数据压缩、日志追踪和请求限流也有类似价值。技术人员维护共同能力，业务开发者声明业务需要的角色、事实和办理结果。能力升级后，可以通过适配与配置作用于多个场景。

## 通过 APP 拦截接入 Java 技术服务

技术服务不必都由 S++ 编译器预先内置。技术人员可以用 Java 实现新能力，再由 APP 将它接到场景或原子服务的调用过程。SPP 仍只表达业务，APP 说明作用于哪些服务、何时执行，PHY 指定实际 Java 类与配置。

例如，要求“商店的所有服务都记录调用耗时”，不用逐个修改付款、下单和查询场景。Petstore 的 [技术服务 APP](../../demos/petstore/src/main/spp/petshop/technical-services.app) 已经这样配置：

```app
technical services { invocationTrace; }
intercept services {
    before: invocationTrace;
    after: invocationTrace;
    failure: invocationTrace;
}
```

`invocationTrace` 是技术能力的名称，`intercept services` 匹配当前业务域全部生成服务，包含场景、普通查询与更新以及量子服务。若只观察场景，可以用 `intercept scenarios`；若只观察指定服务，可以用 `intercept findBuyer, reserveShopPet`。这是技术绑定，不是让业务场景调用一个日志原子服务。

[技术服务 PHY](../../demos/petstore/src/main/spp/petshop/technical-services.phy) 为这个名称指定实现：

```phy
phy {
    technical service invocationTrace {
        implementation: "free.servpp.service.technical.InvocationTraceService";
        config logger = "spp.petstore.invocations";
    }
}
```

接入新能力时，Java 类实现框架的 `TechnicalService` 接口，放入应用运行时类路径；APP 声明名称与拦截范围，PHY 绑定类名与参数。第27章将沿这个接口实现一个慢调用观察服务。

三个阶段有明确含义：

|阶段|执行时机|典型用途|
|before|业务服务调用前|技术访问控制、调用开始记录|
|after|业务调用正常返回后|耗时、校验结果和调用完成记录|
|failure|技术错误向外传播时|故障诊断和告警记录|

`after` 表示方法正常返回，不保证业务通过校验，也不代表外层事务已经提交。预约失败经过 `fail` 处置后正常返回，场景也会进入 `after`。技术服务需要按这些语义记录结果，不能只看到 `after` 就认定付款成功。

当前接口提供服务名称、类别、可信调用头、耗时、校验结果及技术错误等只读元信息，不提供可改写的业务参与者。它直接适合调用观察和基于调用身份的技术控制；修改数据、替代查询或改变返回内容，需要相应适配接口。分离使 Java 技术能力能够持续扩展，同时保持业务事实与规则的维护位置明确。完整协议见 [APP 技术服务与服务拦截](../references/app-technical-services.md)。

## 技术优化必须兑现业务约定

技术策略可以改变如何执行，业务目标和规则仍需要保持。例如，商品名称展示可以接受一定时间的缓存，付款成交则不能根据缓存余额直接覆盖账户。订单列表可以只返回摘要，办理退货仍需要取得判断资格所需的事实。

因此，分离需要双方协作：业务明确事实用途与结果要求，技术选择相应策略。技术层不能为了提速省略资格校验，也不能为了提高成功率悄悄放宽量子成交下限。缓存时效、失败恢复和接口输出都要符合相应业务约定。

本篇下面几章将沿性能、安全、可靠执行和运行治理，说明技术服务可以怎样提升系统能力。这些服务可以由运行时、接入设施或适配器提供，不要求每项技术能力都成为一个远程微服务。
