# 事务边界与嵌套传播的分层评估

> © 2026 S++ project contributors. All rights reserved. [Book copyright](https://github.com/lidonge/spp-examples/blob/main/book/COPYRIGHT.md).

业务层使用以下已确认语法；实现策略从 APP 的原子更新服务绑定解析，不再从 SPP 选择。

SPP声明需要保持事务一致性的操作范围，不在业务语法中选择quantum、Saga、AT等实现模式。在事务范围内，量子属性自动纳入量子一致性保障；普通属性仍需相应一致性机制，不能仅凭包含量子属性就认为整个事务已获得同样的保障。

## 业务人员需要决定什么

业务人员需要知道哪些业务结果必须共同成立，以及一个子步骤失败或外层业务失败后哪些结果应保留。这些约定会改变业务事实，不能由APP部署配置悄悄更改。

| 业务约定 | 内层失败 | 外层失败 | 可参考的Spring传播行为 |
| --- | --- | --- | --- |
| 内外层共同提交、共同撤销 | 整体不能成功提交 | 内层结果也撤销 | REQUIRED |
| 内层可以局部撤销，但成功结果仍属于外层 | 撤销内层后，外层按显式失败处理决定是否继续 | 内层成功结果也撤销 | NESTED |
| 内层是独立提交单元 | 内层撤销，外层按显式失败处理决定是否继续 | 已提交的内层结果保留 | REQUIRES_NEW |

这些是用于SPP设计讨论的业务结果约定，不承诺与Spring的调用链、异常策略或物理实现完全等价。[Spring官方说明](https://docs.spring.io/spring-framework/reference/data-access/transaction/declarative/tx-propagation.html)中，REQUIRED共享物理事务，REQUIRES_NEW独立提交，NESTED通常使用同一事务的保存点。

例如订单创建与库存预占需要一起成功或撤销。可选的赠品分配若允许局部失败，应显式说明失败后可以继续下单；成功分配仍随订单整体提交或撤销。若申请受理事实必须在后续处理失败时保留，那么受理就是一个独立业务提交单元，应在业务层明确表达。

局部失败并不自动意味着业务可以继续；SPP仍需显式的失败处理。独立提交也不能继续被理解为外层整个代码范围都能一并撤销：其独立边界必须对业务设计者可见。

## 建议的分层与默认行为

- SPP约定事务范围及影响业务结果的嵌套传播语义；普通嵌套默认加入外层，共同提交和撤销。只有需要特殊结果时才显式选择局部撤销或独立提交。
- APP将业务约定绑定到事务实现策略，PHY提供资源及能力。连接、保存点、资源挂起等机制不要求业务人员描述。
- APP／PHY不能静默改变业务声明的提交及失败结果；不支持某项语义时应报告能力不匹配，而不能自动降级成另一种业务结果。
- 技术审计等由框架提供的独立持久化可在APP／PHY处理；只有业务要求独立保留的业务事实，才需要在SPP声明独立提交范围。

因此，不必要求业务人员学习Spring全部传播选项，但需要让他们能够表达“共同提交”“可局部撤销”“独立提交”。采用 Spring 名称表达这些提交关系；这些名称不是事务实现模式。


## 已确认语法

```spp
transaction {
    updateOrder(order);
    transaction NESTED { allocateGift(order, gift); }
    transaction REQUIRES_NEW { recordAcceptance(acceptance); }
}
```

不写传播名称等同于 REQUIRED，也可以显式写 `transaction REQUIRED`。事务体可以直接嵌套事务。SPP不定义try/catch/throw。普通check失败只结束block，缺省不引起回滚；显式checkXXX,breakTransction;失败撤销当前边界，量子服务的成交约束失败同样绑定撤销。撤销后是否继续后续场景语句仍待明确。

REQUIRED 内层失败会将共享边界标记为只能撤销，后续执行也不能使已经标记只能撤销的共同边界重新提交。NESTED 的局部失败可撤销内层，成功的内层结果仍随外层撤销。REQUIRES_NEW 挂起外层资源及撤销登记，独立提交结果不登记到外层撤销列表。

## 当前实现范围

生成器根据 APP 原子更新服务的事务绑定解析每个边界的实现策略；同一共同提交边界的策略必须兼容，独立提交边界单独解析。只有查询和检查的边界默认使用本地 AT 协调。策略冲突在生成阶段报错。现阶段同一边界混用 AT 和 QUANTUM 也会报错；这不意味着业务层需要选择它们，而是 APP 配置需要提供统一策略。

本地 JDBC 实现提供资源挂起和保存点。嵌套传播要求外层已经具有 JDBC 资源，NESTED 不能在局部范围内加入新的资源；这些条件不满足时明确拒绝。Saga、TCC 当前不支持这些嵌套源边界；没有该能力的资源不能被当作具备保存点的强一致事务。REQUIRES_NEW 可能与外层持有的数据库锁冲突，不能承诺访问同一被锁记录仍可独立提交。不同边界共享的内存对象也不能代替独立的数据库事实。

## 查询边界与量子域

普通参与者在事务内查询默认生成锁定读取；混合参与者只有本事务也修改普通事实时锁定，只有量子变化时不加普通读锁。量子事实逻辑归量子域，实际数据库/TCC/专用量子服务由APP/PHY选择。业务不写forupdate，事前资格查询放在事务外。参见[事务读取规则](spp-transaction-reads.md)。

业务事务宜保持最小必要范围：准入、独立查询和不依赖受保护事实的计算在事务外；普通事实查询与计算可由可靠乐观基线保护，事务内保留原子条件写入及必须共同提交的变化。不能混用重新查询的事实与旧计算结果。Petstore全部场景的实际选择见[边界审查](https://github.com/lidonge/spp-examples/blob/93d4b68831f1812794e173fd943a77e3be21517a/demos/petstore/docs/transaction-boundary-audit.md)。

## 事务外读改写的默认乐观保障

普通参与者在事务外查询、校验和计算，事务内更新时由APP缺省使用查询基线作原子条件提交。普通事实与物理修订标记一次读取，基线随固定实例、集合补全和同JVM跨域投影传递。条件更新冲突撤销绑定事务；纯准入读取和量子变化不纳入普通版本检查。

本地JDBC仓储将量子属性从普通快照中分离，查询时由量子权威存储补全；量子成交不推进普通修订标记。事务内不需要为了乐观提交重新查询和重复check。仍选择在事务内查询普通事实时，既有自动锁定规则继续有效。见[默认乐观保障、资源组合及兼容限制](spp-optimistic-participant-facts.md)。
