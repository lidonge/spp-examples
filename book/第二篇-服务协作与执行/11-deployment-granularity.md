# 第11章 服务最小颗粒度与部署原则

> © 2026 S++ project contributors. All rights reserved. [Book copyright](https://github.com/lidonge/spp-examples/blob/main/book/COPYRIGHT.md).

讨论服务应该拆多细，需要先明确拆分的下限。SPP 的最小服务颗粒度有明确的业务含义：量子服务是一对量子属性组成的守恒服务，其他服务的最小颗粒度是针对一个角色的操作。在这个业务模型中，不再继续拆成更小的服务。

这一边界决定业务职责怎样划分。部署则决定这些职责在哪里运行、怎样使用资源。明确最小服务颗粒度之后，还需要按依赖、通信成本和扩容需要选择部署方式。

## 量子服务以一对属性的守恒变化为最小单位

甲向乙转100元，甲的余额减少100元，乙的余额增加100元。这一对量子属性及其相互对应的变化，组成一个量子服务：

```text
甲.balance：−100元
乙.balance：+100元
变化之和：0
```

只保留扣款或只保留入账，就破坏了资金转移的完整意义。因此，最小量子服务是这一对属性之间的守恒变化，不能把其中某个属性的增减独立拆成更小的量子服务。

库存预占也是如此：同一商品的可售数量减少2件，预留数量增加2件。两个属性可以属于同一个角色，也可以分属不同参与者，关键是它们在同一业务维度上形成真实的来源与去向。

多个量子服务可以组合，也可以合并成一次较大的量子请求提交。请求包含更多属性，不改变量子服务的最小定义；其中每项基本变化仍是一对量子属性组成的守恒服务。

## 其他服务以角色操作为最小单位

普通查询补全一个角色的事实，普通更新保存一个角色的事实；计算与校验则围绕角色完成明确的计算或判断。例如查询 Buyer、保存 Buyer、计算 OrderLine 的金额，都是以角色为业务单位的操作。

角色可能有多个属性，一项操作也可能只使用其中几个属性。这不改变它的颗粒度。例如校验买家资格只读取买家状态，服务仍是在判断 Buyer 能否参与业务；明细计价只使用单价与数量，服务仍是在计算 OrderLine 的金额。

复杂计算可以复用已有计算，完整场景可以组织多个角色操作。但继续把角色中的字段读取、一次乘法或一个条件比较拆成独立服务，就超出了 SPP 定义的最小业务服务颗粒度。它们是角色操作内部的表达。

## 与面向对象中的属性级操作比较

在面向对象的代码中，可以为姓名提供 `getName` 和 `setName`，为地址提供另一组访问方法。一个属性的读取或赋值，就可以成为一个独立方法；从代码操作看，颗粒度可以细到单个属性。

SPP 用角色操作定义业务服务。查询买家补全 Buyer 所需事实，保存买家落实已经准备好的 Buyer 事实。姓名和地址仍然是属性，但各自的访问方法不再被当成更小的业务服务。普通查询与更新由系统内置提供，开发者在场景中安排调用，计算与校验负责表达相应业务规则。

因此，SPP 的服务细化有明确终点：一对量子属性的守恒服务，或者针对一个角色的操作。服务划分依据业务单位，而不是不断缩小方法内部处理的数据。

## 按使用范围查询角色属性

以角色为最小操作单位，不意味着每次查询都要递归取得整个扮演链条中的所有属性。角色服务的业务颗粒度与实际读取的数据量，可以分别安排。

编译时可以收集该角色在场景、计算、校验等业务表达中被使用的属性，形成查询所需的属性集合。生成的默认查询方法只补全这个集合需要的事实，沿扮演关系取得相应来源，不必把每一层扮演者的全部资料都读下来。

例如 Buyer 由客户实体扮演，报价只使用会员等级，购买校验使用客户状态，下单使用收货地址。编译时收集这些用途后，默认查询可以取得这些所需属性及必要身份信息，而不读取没有被业务使用的其他客户资料。查询仍然针对 Buyer，角色的最小服务颗粒度没有改变，数据库读取、远程传输与映射的数据量却可以减少。

## 用多级缓存减少重复读取

角色查询还可以使用请求内缓存、进程内共享缓存等多级本地缓存。一次场景多次使用同一实体的事实，可以复用已读取的数据；不同请求反复读取相对稳定的事实，也可以按相应策略共享缓存。

对于来自远程业务域的实体，本地缓存尤其有价值。例如商品名称和分类不需要每次使用时都重新访问产品域，可以缓存远程实体的所需事实，再按扮演关系补全本地角色。缓存命中时，减少的是重复的远程访问和等待。

这些都是业务系统常用的优化手段，可以由内置查询结合 APP/PHY 配置承接，开发者仍在场景中调用角色查询。缓存应按业务要求刷新或失效；资金和库存的实际成交仍须使用量子执行机制认可的事实。

属性按需查询减少单次读取的数据量，多级缓存减少重复读取的次数。二者都能缓解角色包含较多属性、扮演链较长带来的性能成本，无需把角色服务拆成一个个属性级服务。分析与缓存的具体条件见附录 C 的 C13 节。

## 计算和校验优先本地部署

明细计价、折扣计算和资格校验可以保留各自的服务定义，并在场景所在进程执行。参与者事实已经准备好时，本地计算与校验直接使用这些事实，避免为短小公式和条件增加网络往返。

角色操作和量子服务可以独立定义、复用与组合，一个部署单元却可以承载多个服务。业务模型保持最小职责，运行结构按实际成本组合它们。

## 查询、量子交易和保存按依赖安排

普通查询根据数据所在位置选择本地或远程执行。需要同时取得的独立角色事实，可以并发查询。若产品目录需要单独扩容，或者客户域由另一团队运营，可以通过相应域的远程服务取得事实。

同一事务边界内，编译器把量子交易提前到普通更新之前，量子服务可以乱序执行或合并请求。量子结果补全后，场景按需要用串行组安排补充计算与校验，再并发执行输入完整的普通更新。部署应支持这些业务依赖，并控制通信与协调成本。

业务颗粒度与部署颗粒度不必一一对应。按角色划分的客户、产品和商店职责，可以部署在同一个进程中，也可以根据容量和维护责任分开部署。“共置”就是把多个服务放在同一个进程里运行，例如客户、产品和商店服务都在同一个 Java 程序中运行，可以直接本地调用。职责归属继续保持，变化的是实际调用路径与资源。

## 部署必须兑现事务边界

Petstore develop 把四个域的服务放在同一个进程中运行，并使用 LOCAL；testing 拆成客户、产品和商店三个应用。两种部署使用相同业务模型，却有不同的通信与提交条件。

多个服务在同一个进程中运行并使用共同资源时，可以在同一本地事务中处理量子变化与普通更新。拆成不同进程后，需要实际支持的协调机制，或明确的分阶段成交与恢复安排。只把部署名称改成“分布式”，不能自动获得共同提交能力。

先按明确的最小颗粒度建模，再按业务依赖、通信成本、扩容需要和事务能力部署，才能既保留细致的角色服务，又减少完整场景的响应时间成本。
