# 第2章 服务等于参与者乘行为

> © 2026 S++ project contributors. All rights reserved. [Book copyright](https://github.com/lidonge/spp-examples/blob/main/book/COPYRIGHT.md).

“转账”是一个行为名称，一个行为是如何形成业务的，需要知道谁提供资金、谁接收资金、金额是多少，以及转账满足什么约束。反过来，两个账户放在一起，也不会自行完成转账。参与者与行为共同构成有业务意义的活动。

“服务＝参与者×行为”中的“服务”，采用传统意义上的宽泛概念，例如通常所说的下单服务、支付服务：参与者共同完成一项业务，形成符合目标的结果。乘号强调双方共同成立：行为需要参与者承载，参与者需要进入行为才能产生业务结果。

SPP 进一步把这项业务中的**服务**与**场景**区分开来。服务承担明确的业务职责，场景围绕完整业务目标组织参与者与服务。本章先说明共同的业务模型，再说明它怎样映射到这两个概念。

## 一个简单的表达

把一次业务活动写为：

```text
B = p × b
业务活动 = 参与者 × 行为
```

其中，p 表示参与者或参与者组合，b 表示具有业务目的的行为，B 表示形成目标与结果的业务活动。传统意义上的一个完整业务服务可以由多项活动组成，因而写为各项活动的组合。完整记号与适用条件见附录 A。

这里的乘法是一种建模表达。它不意味着可以把账户数值和程序方法直接相乘，也不意味着任意业务步骤都天然服从普通代数的运算规则。它让我们检查一个服务定义是否缺失参与方、行为或结果。

## 参与者决定行为的具体含义

同样是支付，买家向商家付款、商家向买家退款、结算账户向钱包充值，参与关系各不相同。把这些活动都写成一个名为 pay 的方法，很难看出它们的业务区别。模型需要明确谁承担哪个角色，行为改变哪些事实，以及通过什么合约表达本次约定。

参与者也不等同于接口里的一组基本参数。账户号可以定位账户，却不能完整表达付款方的资格、账户事实与身份确认状态。金额需要属于明确的付款约定，否则调用者难以判断这个数字究竟是报价、实付还是退款。所以参与者不是传统意义上的Class，而是需要具备一定的角色信息。

## 从完整业务到服务与场景

通常所说的“订单付款服务”，需要查询买家、商家和订单，确认付款资格，准备金额，完成资金转移，并记录订单状态与办理凭证。这些活动共同兑现“完成订单付款”的目标。

在 SPP 中，它们有两种不同的组织责任：

| 概念 | 订单付款中的含义 |
| --- | --- |
| 服务 | 查询参与者、检查资格、准备金额、转移资金、保存订单等明确职责 |
| 场景 | 组织买家、商家、订单与付款合约，组合所需服务，表达顺序、事务边界与完成要求 |

例如，资金转移服务说明买家钱包减少、商家资金增加；付款场景还要说明该付哪笔订单、金额从哪里取得、具备什么资格，以及资金变化怎样与订单记录共同形成付款结果。仅调用资金转移，不能代替这一整项业务。

因此，分析时先说清楚“买家与商家按照付款约定完成订单付款”，再识别其中的服务职责，并用场景组织它们。模型从业务目标出发，SPP语言把局部职责与整体协作分别表达。
