# 第20章 量子属性调用范围与守恒成交

> © 2026 S++ project contributors. All rights reserved. [Book copyright](https://github.com/lidonge/spp-examples/blob/main/book/COPYRIGHT.md).

钱包余额、商家资金与库存数量经常面临并发变化。它们的更新不能仅依赖“查询时足够”这一判断，还需要实际成交时的范围控制和一致性保障。量子属性与量子服务将这种需求显式表达出来。

## 属性与增减

Petstore 声明钱包为量子属性，充值服务描述双边变化：

```spp
quantum update transferWalletFunds(
    Buyer, SettlementAccount, WalletFundingAgreement) {
    SettlementAccount.balance -= WalletFundingAgreement.amount;
    Buyer.wallet += WalletFundingAgreement.amount;
}
```

服务说明变化关系，调用方通过 bounds 说明本次范围。钱包的上下限通常定义在钱包角色的属性中，场景需要先查询钱包，取得这些限制，再将它们用于本次量子服务调用。服务因此可以保持增减职责，同一个服务能够处理具有不同限制的钱包。

## 场景先查询钱包限制

例如，普通钱包的余额下限为 0 元、上限为 10,000 元；允许透支的钱包，余额下限可以是 −500 元。这些限制属于具体钱包的业务事实，不宜在转账服务中统一写死为“余额不得低于零”。

付款场景先查询付款钱包，取得余额下限；充值场景先查询收款钱包，取得余额上限。转账同时涉及来源和去向时，场景取得双方的相应限制，再通过 bounds 传给量子服务。例如，向余额为 9,800 元、上限为 10,000 元的钱包转入 300 元，就不能满足其成交范围。

查询限制与查询余额承担不同职责：前者取得本次成交必须遵守的规则，后者可以用于展示或事前判断。场景把查询到的限制用于调用，量子执行则针对实际成交时的余额检查这些限制；不能只凭查询时的余额判断本次交易一定能够成功。

## 范围在成交时生效

两笔请求都查到钱包 100 元，各自要付 80 元。事前校验可以都通过，实际成交却最多允许其中一笔在不透支规则下成功。量子实现读取并处理当前值，在提交前检查约束。

上下限在调用前求值，null 表示关闭对应方向检查。它不表示未知金额，也不替代支付来源的业务依据。资格条件仍由场景显式校验。

## 按真实关系守恒

付款的来源减少与去向增加应保持相同金额。库存预占则把数量从 available 转向 reserved，发货再从 reserved 转向 sold。不同商品分别守恒，不能用另一商品的增加掩盖本商品的损失。

资金与库存具有不同维度，不属于同一个数值守恒等式。场景可以要求它们协作，实施时需要各自守恒组和整体事务或恢复计划。

## 成交结果与参与者回填

成交之后，执行框架把本次结果回填参与者。该结果说明这次成交产生的事实，不能理解为跨多个来源同一时刻的完整快照。后续交易还可能继续修改余额。

普通输入在准备完成后应保持约定稳定，动态量子事实由量子执行机制处理。业务层不能绕过量子服务直接保存非零余额变化。

## 全自动反交易

量子服务支持全自动反交易。需要撤销原量子成交时，系统依据原成交记录，对原参与者执行相反的增减量，无需业务开发者另写反交易服务或对应的补偿交易。

例如，原交易从甲钱包转出 100 元、向乙钱包转入 100 元，反交易就从乙钱包转出原来的 100 元、向甲钱包转入 100 元。系统恢复的是这笔交易的影响，而不是把双方余额覆盖成交易前的快照，因此可以保留其他交易产生的变化。原交易定位、反向执行、防重与技术失败恢复由系统承接。

业务场景中其他失败所需的业务处置仍要明确，例如取消订单、退回实物或保留申请等待重办。这些处置不要求业务人员重新实现量子服务的反交易。下一章进一步区分回滚、反交易与业务补偿。
