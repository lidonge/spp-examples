# 第19章 事务边界执行计划与部署能力

> © 2026 S++ project contributors. All rights reserved. [Book copyright](https://github.com/lidonge/spp-examples/blob/main/book/COPYRIGHT.md).

“这些变化必须共同成立”是业务要求，“使用什么资源和协议完成”是实现问题。SPP 用 transaction 表达边界，APP 选择策略，PHY 提供真实资源。生成的执行计划把三者连接起来。

## 普通更新默认使用乐观锁

SPP 的普通 update 默认使用乐观锁。场景查询参与者时，系统保留查询基线；场景完成计算与校验后，内置更新服务依据基线进行条件更新。如果相关普通事实已被另一个请求修改，本次更新就不能直接覆盖对方的结果，而应报告并发冲突。冲突后的重试或技术恢复策略在 APP 层定义。

例如，两个请求都读到同一份客户资料。第一个请求修改地址并成功保存，第二个请求仍拿着原资料修改联系电话。第二次保存需要发现查询基线已经变化，不能把整份旧资料写回，导致地址又变成旧值。乐观锁让查询和业务计算不必一直占有记录锁，同时在实际更新时检查是否发生竞争。

普通更新默认的乐观锁，与事务内查询的自动锁定可以同时存在。查询放在事务外时，不提前锁定记录，更新依靠查询基线作条件提交；查询放在事务边界内时，系统按参与者的属性和本事务的修改范围决定是否锁定读取。

| 查询对象 | 事务内的读取方式 |
| --- | --- |
| 普通参与者 | 自动锁定读取，当前 JDBC 实现使用 `SELECT ... FOR UPDATE` |
| 量子事实 | 不添加普通记录读锁，由量子实现保障并发成交 |
| 同时含普通与量子属性的参与者 | 本事务也修改普通属性时锁定普通事实；只有量子变化时不添加普通读锁 |

SPP 业务源码不需要显式写 `select for update`，但这不意味着运行时没有锁定读取能力。例如，把普通客户资料查询放在事务外，系统采用查询基线保护后续保存；放在事务内，内置查询会锁定相应普通记录。锁定普通记录也不能理解为锁定钱包余额等量子事实，其增减仍由量子服务处理。具体规则见 [事务内查询与量子事实](../references/spp-transaction-reads.md)。

## 本地共同提交

Petstore develop 使用 LOCAL。相关域同 JVM，并共用满足约定的数据库、schema 和连接资源，量子变化与普通更新进入同一个本地事务。失败处理在这一资源范围内进行。

相同数据库名称不足以证明共用同一事务连接，跨进程也不能因为访问同一数据库便自动获得 LOCAL。编译和启动检查需要核对实际资源身份。

## 分阶段执行

非 LOCAL 配置下，集中量子组可以先成交，普通更新按模式分组执行，不同已提交阶段通过 Saga 恢复。已经提交的量子变化不能再依赖后续普通数据库的回滚撤销。

执行计划因此需要明确恢复能力。缺少恢复约定的组合应被拒绝，不能由框架猜测业务补偿。跨阶段共同成功的含义也应与单资源原子提交区分。

## 嵌套边界

REQUIRED 加入当前边界，内层结束不额外提交。付款场景中的嵌套 REQUIRED 用于表达逻辑范围，不能把它读成先付款、再独立提交订单。

REQUIRES_NEW 形成独立边界，其结果不会自动归入外层恢复链。例如，付款中的内层 REQUIRED 与外层一起完成；独立开户若采用 REQUIRES_NEW，则外层失败时该开户可能已经完成，业务需要另行处理。示例后端的传播支持范围见附录 E。

## 编译器自动形成量子优先的执行计划

普通更新由系统内置提供，开发者不编写或修改其实现。更新内部不做业务查询、计算或校验；所需事实由场景的查询、计算和量子服务补全，内置更新使用完整输入保存结果。

普通更新不会影响量子交易的结果，量子交易自身可以交换执行次序。因此，在同一个事务边界内，SPP 编译器自动将量子交易提前到所有普通更新交易之前；量子交易可以乱序执行或合并提交。若成交后还要计算凭证内容、校验办理结果，开发者用串行组安排这些场景步骤，待保存输入完整后再并发执行普通更新。执行计划由服务职责与交换律形成，无需通过普通更新互调来维持先后顺序。运行层还需提供事务上下文、资源调度、汇合与失败处理，使并发保存兑现该边界的提交与恢复约定。这里的“量子服务之后”表示执行阶段的先后；LOCAL 下仍可在共同本地事务中最终提交。

## 为什么 SPP 不使用异常处理语法

SPP 不提供 `try/catch/throw`，是为了让场景表达业务规则与办理过程，技术失败的处理策略在 APP 层定义，由运行时与 PHY 提供的资源能力执行。这遵循业务与技术分离的原则：业务人员需要说明什么条件下可以办理、哪些变化应当共同成立，而不必了解数据库连接、网络超时或底层异常类型。设计文档将错误拦截与处理从业务流程中独立出来，[参与者执行约定](../references/spp-participant-execution.md)进一步明确技术异常不能成为 SPP 的业务分支条件。

首先，业务条件不满足是一种需要明确表达的业务结果。例如，订单已经发货，不符合“取消未发货订单”的条件，场景通过校验服务拒绝办理。普通校验失败结束当前块，guard 校验决定是否执行它包围的步骤；需要撤销当前事务时，用 `breakTransction` 明确声明。这样，阅读场景就能看出办理条件和失败影响，不必把业务规则藏在某个异常类或 catch 分支中。

其次，技术故障不能被当作业务事实。例如，查询订单时数据库连接失败，并不说明订单不存在；付款请求超时，也不说明付款没有成交。若场景捕获这些故障后直接走“订单不存在”或“重新付款”的分支，就可能作出错误的业务决定。APP 层应定义结果确认、重试和技术恢复策略，运行时根据实际执行与提交证据落实这些策略，不能把尚未确认的结果伪装成确定的业务条件。

这种分工也使场景不依赖具体技术实现。同一付款业务，无论使用本地数据库还是远端量子服务，业务目标与规则都应保持一致。如果场景要分别捕获数据库异常、通信异常和各提供方的错误类型，更换存储或部署方式就会迫使业务代码一起修改。在 APP 层定义这些技术处理策略，业务人员才能集中检查角色、校验、计算和成交要求；生成的 Java 与运行时仍可使用异常处理来落实这些约定。

但业务与技术分离并不意味着业务人员不必考虑失败。例如，申请已经受理，后续办理无法完成，是保留申请等待重办，还是取消申请并退还费用？这些选择会改变业务结果，必须由业务人员明确。

## 失败补偿

SPP 层明确处理业务层面的失败。失败补偿回答的是：业务条件已经明确不满足，已经产生的业务结果应当怎样处理？这需要业务开发者明确规定，因为相同的业务失败在不同业务中可能有不同的处置方式。

例如，库存不足导致订单无法履约，顾客可能接受等待补货，也可能要求取消并退款。框架能确认库存占用和付款的实际结果，却不能替顾客与商家选择如何继续。`transaction { ... } fail { ... }` 用于表达这类失败后的业务操作。系统先完成事务执行与技术恢复，再把失败事实交给相邻的 fail 块；fail 中需要保存业务处置时，另开显式事务。

补偿操作首先取决于失败发生时，哪些业务事实已经成立：

| 失败情况 | 业务开发者需要明确的操作 |
| --- | --- |
| 准入校验失败，尚未发生业务变化 | 拒绝办理并说明原因；没有实际扣款就不应退款 |
| 库存已经占用，后续业务校验拒绝订单 | 是否取消本次申请；取消时释放本次实际占用的库存 |
| 付款已经成交，商家确认无法履约 | 是保留付款等待补办，还是取消订单、退款并释放相关占用 |
| 申请独立受理成功，后续审批未通过 | 是保留申请等待重办，还是将申请改为已拒绝或已取消；已收费用如何处理 |
| 商品已经交付，后续业务无法完成 | 按约定安排退货、退款或其他补救；改回订单状态不能代替实际退货 |

这里列出的是需要作出的业务决定，不能机械地把每次失败都变成“逆序撤销所有步骤”。共同事务中尚未提交的变化可以由技术回滚撤销；量子服务已提供全自动反交易，业务开发者无需另写对应的反交易或补偿交易。业务仍需明确取消订单、释放业务占用或继续履约等处置。业务完成后另行申请的部分退款、扣费等，则应按其自身规则办理，不能把原付款记录当作从未发生。

补偿操作也需要遵守这一分层。例如，退款申请不符合业务规则，属于 SPP 需要明确处理的业务失败；执行退款更新时超时，则属于 APP 需要处理的技术失败。SPP 规定退款的资格、金额及业务结果，APP 规定更新结果的确认、重试和恢复，不能把通信超时直接变成“退款被业务拒绝”。

## 实例：预约已受理，库存不足时记录拒绝

Petstore 的预约场景先保存受理申请，再尝试预占库存。假设可用库存为 10 件，顾客申请 11 件：业务已经受理，但预占不能完成。这个场景选择保留原预约号，并把申请记为“已拒绝、库存不足”。下面摘自 [真实预约场景](../../demos/petstore/src/main/spp/petshop/reservation/petshop-scene-reserveShopPet.spp)，省略前面的准入查询和计算：

```spp
transaction { insertPetReservationAgreement; }
prepareReservationInventory; findStockLine; identify(StockLine[]);
transaction {
    reserveRequestedInventory bounds {
        StockLine[].available: [0, null]; StockLine[].reserved: [0, null]; };
    confirmPetReservation; updatePetReservationAgreement;
} fail {
    if (ResultInfo.failure.recoveryStatus == "ROLLED_BACK" || ResultInfo.failure.recoveryStatus == "REVERSED") {
        findStockLine; identify(StockLine[]);
        rejectPetReservation;
        transaction { updatePetReservationAgreement; }
    }
}
```

第一个 transaction 独立保存受理申请，后面的预占事务失败不会自动删除它。预占成功时，场景将申请改为 RESERVED；预占失败时，系统先回滚未提交变化，或对已成交量子阶段自动反交易，再进入 fail。

`ResultInfo` 是场景内置的系统参与者，不需要在入口中声明。样例只在 recoveryStatus 为 ROLLED_BACK 或 REVERSED 时办理拒绝：前者表示相应事务已回滚，后者表示已提交阶段已恢复。它随后重新查询库存，调用 `rejectPetReservation` 判断业务原因，再用新的 transaction 保存申请状态。这些查询和保存属于失败后的处置，不属于已经失败的预占事务。

[拒绝计算服务](../../demos/petstore/src/main/spp/petshop/reservation/petshop-35-reservation.spp)将申请标记为 REJECTED，并根据恢复后的库存与申请数量区分 INSUFFICIENT_STOCK 和 RESERVATION_NOT_COMPLETED。因此，库存 10 件、申请 11 件的结果是保留原预约号、记录库存不足，库存仍为可用 10 件、预占 0 件。如果预占本可成功，只是后续普通保存失败，恢复后则记录“预约未完成”，不能误记为库存不足。

fail 没有手写“把库存加回来”：这由系统回滚或自动反交易完成。它表达的是业务选择——保留受理记录，并记录申请的最终拒绝状态与原因。

结果不明时，系统会提供 RECOVERY_REQUIRED，样例不会把申请判为已经安全拒绝。fail 可以记录待核对的业务信息，但技术失败仍交给 APP 处理，不能因执行过 fail 就视为恢复完成。处置完成时，系统结果仍为 FAILED，handled 为 true，表示原事务失败已处置，而非原事务成功。当前支持串行场景中的外层事务 fail；多个入口合约时用 `fail(目标合约)` 明确关联。完整协议与限制见 [失败处理与系统结果](../references/spp-transaction-failure-handling.md)。

## 技术失败在 APP 层定义

更新服务超时导致结果不明，是典型的技术失败：更新可能尚未提交，也可能已经提交而确认响应未到达。APP 层需要定义如何依据原请求身份查询执行结果、什么条件下允许重试，以及无法自动确认时如何保留技术恢复待办并转交运维处理。运行时和 PHY 的存储、通信能力负责执行这些策略。

例如，订单状态更新超时，SPP 不需要增加“捕获超时后取消订单”的业务分支。APP 应先确认原更新是否完成；已完成就恢复相应执行结果，未完成则按约定重试，仍不明确就保留待确认状态。超时本身不能作为触发业务退款或取消的依据。

同样，业务补偿中的退款或库存释放如果遇到技术故障，其进度记录、防重、结果确认和技术恢复也在 APP 层定义。只有业务上的退款或释放确实完成，才可以报告补偿完成；技术重试不能造成重复退款或重复释放。

## 对外判断实际结果

请求失败可能意味着未提交，也可能意味着部分阶段已提交，或结果暂时未知。场景的实际状态应根据成交与恢复证据判断，不能直接从一次 HTTP 错误推断所有资源已经回滚。

明确事务语义与部署能力，才能让业务边界成为可靠承诺。详细支持范围见附录 D 与 F。
