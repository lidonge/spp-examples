# 第30章 报价下单付款与发货

> © 2026 S++ project contributors. All rights reserved. [Book copyright](https://github.com/lidonge/spp-examples/blob/main/book/COPYRIGHT.md).

沿用第六篇第29章的基线：买家钱包 500 元，可售库存 10 件。买家是 VIP，选择单价 60 元的商品两件。本章把同一订单拆成报价、下单、付款和发货，观察每项完整活动如何组织不同类别的服务。

## 报价计算候选约定

小计为 120 元，VIP 折扣为 12 元，折后 108 元达到免运费条件，订单总额为 108 元。计算规则见 [订单计算](../../demos/petstore/src/main/spp/petshop/order/petshop-20-calculations.spp)。

报价使用查询得到的商品价格、购物车数量和会员等级。计算形成候选订单，不直接保存成交。明细保留名称、数量、单价与金额，订单保留折扣、运费和总额。商品价格虽可量化，却是报价依据；价格调整与实际资金转移承担不同职责，不能因为字段都是数字就都定义为量子服务。

如果商品后来调价，已经保存的成交明细继续使用原价。业务定义说明需要保留成交约定，APP 的快照映射负责让保存和查询兑现这一要求。

## 下单把约定与库存预占联系起来

[下单场景](../../demos/petstore/src/main/spp/petshop/order/petshop-scene-placeShopOrder.spp) 的流程可以按依赖分成四段：

1. 准备商品选择，并行查询买家与商品目录。
2. 定位并查询购物车，检查内容，计算订单报价。
3. 准备库存参与者，查询库存，检查预占资格，准备订单和购物车变化。
4. 在事务边界内保存订单明细、订单、购物车和回执，并完成库存预占。

第一段的两项查询互不依赖。库存查询却需要先由订单准备商品关系，不能与最初的所有查询随意放进同一个并行组。这对应第二篇第9章所讲的输入依赖。

预占将两件从可售转为预留，结果是可售 8、预留 2、已售 0。供应来源仍为 −10，该商品合计仍为零。事前“库存够不够”的判断不能阻止其他订单同时下单，因此可售下限还必须在量子成交时检查。

源码中既有量子更新，又有普通保存。编译器根据准备依赖安排量子成交和后续更新。当前下单在事务内还有 `preparePurchaseReceipt`，因此不能把事务中的每一行都当作可以同时执行的普通更新；计算结果必须先准备，依赖它的回执保存才能执行。普通更新内部不会补查或计算这些内容，串行依赖仍在场景中可见。

## 付款明确金额与参与者

付款不再查询购物车，也不重新计算商品折扣。它读取已经形成的订单，确认买家归属与付款资格，准备 108 元付款约定和回执，然后执行资金转移与普通保存。

[付款源码](../../demos/petstore/src/main/spp/petshop/payment/petshop-scene-payShopOrder.spp) 中的事务片段如下：

```spp
transaction {
    transaction REQUIRED {
        payOrderFunds bounds {
            Buyer.wallet: [0, null]; Merchant.cash: [0, null];
        };
    }
    updateShopOrder;
    insertReceipt(PaymentAgreement.receipt);
}
```

钱包减少 108，商家资金增加 108，钱包变为 392。量子服务处理守恒变化，普通更新保存订单与回执。订单更新和回执插入使用已经准备的输入，可以由支持该计划的技术配置安排并发执行。

内层 `REQUIRED` 加入外层逻辑边界，不代表内层结束就完成一笔独立付款。实际资源共同提交还是分阶段成交与恢复，需要看 APP 和 PHY。不能从这段 SPP 单独推断两个数据库具有同一物理事务。

## 发货沿另一对库存属性成交

[发货场景](../../demos/petstore/src/main/spp/petshop/fulfillment/petshop-scene-shipShopOrder.spp) 查询买家与订单，再准备库存并查询，检查订单状态与预留数量，准备发货约定和回执。

量子服务把两件从预留转为已售，结果是可售 8、预留 0、已售 2。普通更新保存发货状态、运单信息与回执。付款维护资金，发货维护库存，两项活动使用不同守恒属性，也有不同完成条件。

## 逐阶段核对同一订单

|阶段|钱包|商家资金变化|可售／预留／已售|需要核对的普通事实|
|下单后|500|0|8／2／0|订单明细、108 元总额、未付款状态|
|付款后|392|+108|8／2／0|已付款状态、付款回执|
|发货后|392|+108|8／0／2|发货状态、运单与回执|

这张表描述假设输入下的业务结果，不能替代运行验证。如果付款超时而结果未知，表中的“付款后”还不能直接显示为失败或成功；必须先由 APP 确认实际成交与保存结果。下一章讨论如何区别失败恢复与正常后续办理。
