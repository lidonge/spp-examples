# 第32章 技术配置部署与综合验证

> © 2026 S++ project contributors. All rights reserved. [Book copyright](https://github.com/lidonge/spp-examples/blob/main/book/COPYRIGHT.md).

前四章已经表达了业务参与者、报价、成交与失败处置。本章沿同一组场景查看技术配置：哪些能力已在 Petstore 中提供，哪些能力可以继续加入，部署改变后如何验证。第五篇讨论的业务与技术分离，在这里应当能落实到文件和结果。

## 先把三个层次放在一起

|层次|付款业务中的内容|主要文件|
|SPP|付款资格、金额、资金转移、订单和回执|付款场景及模型、计算、校验|
|APP|存储映射、请求策略、逻辑绑定、事务及环境选择|petshop.app|
|PHY|数据库、量子存储、协议路由、超时和适配器|petshop.phy|

业务人员检查“谁付款、付多少、何时允许、失败后怎样办理”，技术人员检查保存和调用策略，运维人员检查实际资源与环境。AI 可以帮助修改各层，但业务人员不需要通过审查生成的全部 Java、数据库驱动和部署代码，才能理解付款规则。仍需用运行证据确认工具和技术适配兑现了这些规则。

以下片段分别来自 [商店 APP](../../demos/petstore/src/main/spp/petshop/petshop.app) 与 [商店 PHY](../../demos/petstore/src/main/spp/petshop/petshop.phy)。

## 用存储映射保留成交事实

APP 中的明细表包含：

```app
table SHOP_ORDER_LINES(OrderLine) {
    primarykey(OrderLine.lineNumber);
    auto OrderLine.lineNumber prefix "ORDER-LINE";
    foreignkey(OrderLine.goods) references Goods;
    snapshot(OrderLine.name, OrderLine.unitPrice);
}
```

商品名称另有 `current(Goods.name)` 配置。验证时，先保存一笔订单，再修改产品名称和商品价格，分别查询当前商品与旧订单。前者反映当前事实，后者保留成交名称和单价。这一实验同时检查第三篇的扮演映射与第四篇的存储归属。

## 用请求策略保障重复办理

当前 APP 有以下全局策略和付款入口配置，分别位于 `requests` 与 `scope local` 中：

```app
requests { idempotency retention 3 days; duplicateWindow 5 seconds; }
```

```app
duplicate key(Buyer.membershipNumber, ShopOrder.orderNumber)
    facts(ShopOrder.orderNumber) payShopOrder;
```

PHY 使用 `config requestIdempotencyAdapter = "jdbc";`。页面防重处理短时间重复操作，远程更新幂等处理同一调用的重复传输。付款资格仍由 SPP 检查，不能把防重窗口当成付款业务状态。

验证至少分为三项：短时间重复点击不产生第二笔付款；远程更新以相同身份与内容重放，返回原结果而不重复成交；相同请求身份改变金额或参与者，应被判定为协议冲突。本地调用不额外登记远程请求，不能用一次 LOCAL 调用测试代替远程幂等验证。协议说明见 [调用幂等与界面防重](../references/app-call-idempotency-and-duplicate-guard.md)。

持久适配器还需要核对实际数据源及重启后的记录。声明保留三天并不意味着结果未知的请求到期后可以直接当成新付款，未完成恢复的记录需要相应处理。

## 比较集中部署与拆分部署

develop 的 APP 将客户、产品、库存和商店四个域部署在同一进程，并声明：

```app
transactions {
    mode: LOCAL;
    resource: shopRecordsResource;
    ordinaryUpdates: PARALLEL;
}
```

PHY 将普通记录和量子存储接到对应本地资源。已经准备好、互不依赖的普通更新由该配置安排并发；输入尚未准备好的步骤仍按场景依赖执行。

testing 将客户、产品拆到独立进程，库存与商店同进程，普通库与量子库也分别配置。PHY 提供客户、产品的远程路由与超时，APP 为量子服务选择统一存储，普通更新资源使用相应恢复策略。

业务域划分仍相同，数据库和调用路径发生改变。LOCAL 的共同回滚不能直接推定为跨资源共同回滚；量子先成交而普通更新后失败时，需要依照第四篇第21章确认阶段结果并恢复。配置改变没有免除业务一致性要求。

仓库已有网页流程、重启守恒核对及失败处置记录，具体版本与证据见附录 F。它们证明所记录路径，不能自动证明所有故障组合，也不是性能基准。

## 将性能优化应用到具体查询

在商品浏览中，可以缓存产品名称、说明和展示数据，避免每次沿扮演链重复读取同一事实。查询范围也可以按场景实际使用的属性收集：报价需要价格和资格，商品列表需要展示字段，不应每次递归取回全部参与者属性。

在订单列表中，页面通常只需要订单号、状态与总额，点击详情时才需要明细。按需查询减少后端读取，按需返回减少传输，两项优化要分别测量。部分加载的对象不能被当成完整事实覆盖保存。

这些是结合第五篇第24章提出的改造方案，当前案例尚未证明已经具有完整的多级缓存、编译期属性裁剪和通用返回数据集配置。实施时应补充缓存键、更新失效、权限范围和未加载属性的保存约束，而不是只在场景里删掉查询。

钱包余额和可售库存即使用于页面展示缓存，实际付款与预占也必须按真实成交范围检查。技术优化不能把“缓存显示有两件”变成“这次必然能买两件”。

## 从现有日志样例扩展技术服务

Petstore 已增加 [技术服务 APP](../../demos/petstore/src/main/spp/petshop/technical-services.app) 和 [技术服务 PHY](../../demos/petstore/src/main/spp/petshop/technical-services.phy)。APP 用 `intercept services` 为商店域服务统一安排 `invocationTrace`，PHY 绑定通用 Java 日志实现，记录调用名称、阶段与耗时，业务 SPP 没有增加日志调用。

业务人员仍检查付款金额、订单状态和预约拒绝原因，技术人员通过日志检查实际调用。预约预占失败经过 `fail` 处置后，场景正常返回会记录 `AFTER`；这表示调用正常结束，并不表示预约成功。日志也不打印客户和订单内容。

沿第五篇第27章的接口，可以新增 Java 技术服务并通过 APP／PHY 接入指标、告警或技术访问控制。查询缓存和输出脱敏则使用相应数据适配。样例及验证范围见 [Petstore 技术服务](https://github.com/lidonge/spp-examples/blob/93d4b68831f1812794e173fd943a77e3be21517a/demos/petstore/docs/technical-services.md)。

## 将安全与运行治理应用到办理入口

当前 testing PHY 已声明域间调用令牌配置，但单个令牌不等于完整的用户认证、资源授权和数据保护。生产改造还应围绕付款和订单入口安排以下能力：

|能力|Petstore 中的应用位置|需要验证的结果|
|认证与访问控制|页面与域间入口|调用方身份可信，不能代其他买家操作|
|加解密与脱敏|通信、地址等敏感事实、日志与返回数据|未经授权不能读取敏感内容|
|请求内容指纹|技术请求登记|同一请求身份更换内容能被识别|
|追踪与指标|查询、成交、保存和恢复阶段|能定位耗时及确认各阶段结果|
|限流、隔离与熔断|浏览和更新入口、远程资源|故障不会无限扩散，已受理更新仍可确认|

表中是技术设计与验证任务，不代表这些能力都已经实现。请求内容指纹不能替代身份认证，业务归属校验也不能替代调用方认证；第五篇第25章解释了两者的区别。

浏览页面的推荐或图片可以按策略降级，付款不能在超时后返回虚假的成功或拒绝。追踪信息应关联原请求、量子成交、普通保存与恢复证据，让技术人员能确认结果，而不要求业务人员在 SPP 中编写网络异常捕获。

## 最后形成一份综合验证记录

先用第六篇第29至30章的数值表核对完整业务，再选择取消、退货或预约分支。检查订单状态、回执、资金和库存守恒，以及重复调用、版本竞争、库存不足和结果未知的处理。

性能只保留必要对照：在独立实验副本中，对互不依赖的查询分别使用串行和并行，保持业务规则与部署资源一致；记录端到端延迟、分支重叠、吞吐、错误比例和资源占用。缓存或按需数据若实际加入，则另设对照，避免把几种优化的效果混在一起。实验方法放在附录 C，不在正文重复推导。

报告同时注明源码版本、APP 策略、PHY 资源和覆盖范围。业务正确、技术配置符合预期、部署后结果可确认，三项一起成立，才完成本篇的实践闭环。
